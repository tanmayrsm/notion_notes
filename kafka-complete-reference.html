Chapter 1 — Foundations

What is Apache Kafka?

Kafka is a distributed, fault-tolerant, durable event streaming platform. Think of it as an append-only ledger that sits between your services — every service writes events to it, every interested service reads from it, at its own pace, independently. The ledger never forgets unless you tell it to.

The Problem Kafka Was Built to Solve

In 2010, LinkedIn had hundreds of internal microservices — profile service, job recommendations, people you may know, analytics, activity feed. Every time one service needed data from another, they built a direct point-to-point connection. With 10 services wanting to talk, you get up to 45 different connection pairs. With 50 services, up to 1,225. This grew into an unmaintainable spaghetti of integrations, where adding any new service required coordinating changes across multiple existing teams.

Jay Kreps, Neha Narkhede, and Jun Rao solved this in 2010 by building a universal bus: one central system where everything publishes events, and everything interested reads them. They called it Kafka. It was open-sourced in 2011, donated to Apache in 2012, and the three founders left LinkedIn to found Confluent — whose Docker images (confluentinc/cp-kafka) we use in our cluster today. Kafka now runs at every major tech company: Uber, Airbnb, Netflix, Twitter, PayPal (where you work), and yes — Zomato and Swiggy.

Before Kafka — spaghetti integrations

5 services = up to 20 direct connections. Order Service directly calls Restaurant Service, Notification Service, Analytics Service, Flink. Any one failing can cascade. Adding fraud detection means modifying Order Service code and coordinating deploys. Every connection is a failure point, a version conflict, a deployment dependency.

After Kafka — star topology

Every service talks only to Kafka. Order Service publishes one event. Restaurant Service, Notification, Analytics, Flink, Fraud — each subscribes independently. Adding fraud detection later? Zero changes to Order Service. Zero coordination needed. N services = N connections to Kafka, not N² between services.

In FoodFlash — What This Concretely Means

When a customer places an order, that single event must reach five different systems with completely different concerns. Without Kafka, Order Service would need to know about and call each one. With Kafka, it knows about none of them:

Chapter 2 — Foundations

Log vs Queue — The Core Difference

This is the single most important concept to understand before anything else. A message queue (RabbitMQ, SQS, ActiveMQ) destroys messages after they're delivered. Kafka keeps messages on disk regardless of how many times they've been read, until a time-based retention period expires. This one difference changes everything.

How a Traditional Message Queue Works

Picture a queue as a to-do pile on a shared desk. You add a task, someone picks it up, the task is shredded — gone. That's RabbitMQ. Once a consumer processes a message and sends an acknowledgement, the broker deletes it permanently.

1
Order Service publishes "order created" to RabbitMQ
Message enters the queue. It waits there for a consumer to pick it up.
2
Restaurant Service consumes it — RabbitMQ deletes the message
Restaurant Service receives the message, processes it, sends an ACK. RabbitMQ permanently deletes the message. It no longer exists anywhere.
!
Notification Service, Flink, Analytics — they get nothing
The message is gone. To send it to other services, you'd need to either: (a) publish separate copies to separate queues — now Order Service must know about every consumer, or (b) use RabbitMQ fan-out exchanges — still complex coupling. A new fraud detection service added three months later will never see historical orders. Ever.

How Kafka's Commit Log Works

Kafka is a physical log file on disk — like a ledger. Every message gets a sequential number called an offset and is appended to the end. Consumers read from the log by tracking their position. Reading does not delete. The message stays until the retention window expires.

1
Order Service publishes — message written to disk at offset 1001
Written to partition-0 of order.created on kafka1's disk. Immediately replicated to kafka2 and kafka3 (RF=3). This message will exist on disk for the next 7 days regardless of anything.
2
Restaurant Service reads offset 1001 — message still on disk
restaurant-group reads offset 1001, processes it, stores its bookmark: "I've read up to 1001, give me 1002 next." The message at offset 1001 is completely untouched on disk.
3
Notification Service reads the same offset 1001 — still there
notification-group has its own independent bookmark. It reads offset 1001, sends the push notification, updates its bookmark. Neither group knows or affects the other.
4
Fraud detection added 3 months later — reads the entire history
fraud-group is a brand new consumer group. It has never read this topic before. Kafka has no record of it. With auto.offset.reset=earliest, it starts from offset 0 and reads every single order from the past 7 days (the retention window). No changes to Order Service needed. No re-publishing needed.
7d
After 7 days — broker deletes the segment file
The Kafka broker's log cleaner thread deletes the segment containing offset 1001. This is based on time only — has nothing to do with whether anyone read it. Consumer state (bookmarks) are stored separately and are not deleted here.

Chapter 3 — Foundations

Brokers, Zookeeper & the Cluster

A Kafka cluster is a group of broker processes (servers) coordinated by Zookeeper. Producers and consumers are clients that connect to brokers. Our cluster runs 3 brokers inside Docker containers on your M4 Mac — identical architecture to production, just smaller scale.

What a Broker Is

A broker is a single Kafka server process. Its responsibilities: receive messages from producers and write them to disk, replicate those messages to follower brokers, serve read requests from consumers, and participate in leader election when another broker dies.

In a production cluster at Zomato scale, each broker is a dedicated physical machine with 32+ CPU cores, 128GB+ RAM, and 10TB+ of fast NVMe SSDs — because Kafka's performance bottleneck is disk I/O and network bandwidth. In our local setup, each broker is a Docker container sharing your M4 Max's hardware. Same behavior, same configuration flags, different scale.

Zookeeper — The Cluster's Nervous System

Zookeeper is a distributed coordination service built by Yahoo in 2008. Kafka uses it as a single source of truth for cluster state. Here's what it tracks and why:

Job 1: Broker heartbeats (liveness tracking)

Every broker maintains a "session" with Zookeeper, sending heartbeats every 2 seconds. When kafka1 starts, it registers itself: "I am broker 1, reachable at kafka1:29092." If heartbeats stop for more than 10 seconds (configurable), Zookeeper declares the session expired and broadcasts to all remaining brokers: "Broker 1 is dead." This triggers leader election for any partitions that kafka1 was leading.

Job 2: Partition leader tracking

For each of our 6 partitions, Zookeeper stores: "The leader for order.created partition-0 is broker 1." Producers and consumers ask Zookeeper (or a broker that has cached this info): "Who is the leader for partition-0?" and route accordingly. When a leader dies and a new one is elected, Zookeeper is updated and all clients refresh their routing tables.

Job 3: Topic and configuration metadata

Kafka stores topic configurations (partition count, replication factor, retention settings) in Zookeeper. This is why you need Zookeeper running before you can create topics. Note: Kafka 3.x introduced KRaft mode — Kafka managing its own consensus without Zookeeper. Our setup uses the traditional Zookeeper model for compatibility with our Docker images.

Why Two Listener Addresses in docker-compose?

This is a real production gotcha. Look at our config:

KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://kafka1:29092,PLAINTEXT_HOST://localhost:9092

Two listeners, two different addresses. Why? Because two different "networks" need to reach kafka1:

kafka1:29092 — inside Docker network

When Spring Boot Order Service runs inside Docker, it lives on the same bridge network as kafka1. The hostname kafka1 resolves to kafka1's container IP. Other containers use this address. If they used localhost:9092, they'd be talking to their own container's loopback — a completely wrong address that silently fails.

localhost:9092 — from your Mac terminal

When you run kafka-topics --bootstrap-server localhost:9092 from your Mac's terminal, localhost resolves to 127.0.0.1 on your Mac. Docker maps port 9092 on your Mac to kafka1's internal port 29092. This is how kafka-ui, your terminal commands, and any local test code reach the cluster.

Without this split, you'd have to choose: either local tools work and containers don't, or containers work and local tools don't. The dual listener pattern solves both simultaneously.

Chapter 4 — Core Mechanics

Topics, Partitions & Offsets

A topic is a named category of events. A partition is a physical shard of that topic — an actual append-only log file on disk. An offset is a sequential integer that uniquely identifies each message within a partition. These three concepts are the foundation of everything else in Kafka.

What a Topic Is

A topic is the equivalent of a database table, except it's an append-only event stream rather than mutable rows. When you create the topic order.created, you're telling Kafka: "I want a named category where order-creation events will be stored, accessible to any service that wants them." Topics are identified purely by name — there's no schema enforcement by default (though schema registry can add this).

What a Partition Is — The Physical Reality

When you create a topic with 6 partitions, Kafka creates 6 independent directories on broker disks. Each partition is physically a sequence of segment files:

# Inside kafka1 container, for topic order.created, partition 0:
/var/kafka-logs/order.created-0/
    00000000000000000000.log       # messages: offset 0 → 999
    00000000000000000000.index     # offset → byte position in .log file
    00000000000000000000.timeindex # timestamp → offset lookup
    00000000000001000000.log       # messages: offset 1000 → 1999
    00000000000001000000.index
    00000000000002000000.log       # messages: offset 2000 → present (active)

# kafka2 has an IDENTICAL copy of this directory (it's a replica for P0)
# kafka3 has an IDENTICAL copy too (RF=3 means 3 total copies)

The .log file is a raw binary file — each record is: 8 bytes for offset, 4 bytes for message size, 4 bytes for CRC checksum, 1 byte magic number, 1 byte attributes, 8 bytes timestamp, then the key bytes and value bytes. The .index file maps offsets to byte positions in the .log file so Kafka can jump to any offset in O(log n) time using binary search.

What an Offset Is

An offset is a monotonically increasing integer assigned to each message within a partition. Offset 0 is the first message ever written to a partition. Offset 1001 is the 1002nd. Offsets are per-partition — there's a separate offset sequence for each partition. Message #1001 in partition-0 and message #1001 in partition-1 are completely different messages.

Offsets are how consumers track their position — "I have processed everything up to offset 1001 in partition-0." This bookmark is stored in an internal Kafka topic called __consumer_offsets, which we'll cover in depth in the Offsets chapter.

Why 6 Partitions — The Parallelism Math

The number of partitions sets the ceiling on how many consumer instances can read in parallel. With 6 partitions, you can have at most 6 active readers in one consumer group simultaneously — one per partition. A 7th consumer would sit idle; Kafka cannot split one partition between two consumers.

We chose 6 because it's divisible by 1, 2, 3, and 6 — meaning we can scale Order Service to 1, 2, 3, or 6 instances and partitions will always distribute evenly without any idle consumers. This is a deliberate, permanent architectural choice — you can increase partition count later but reducing it requires recreating the topic and migrating data.

Ordering Guarantees — What's Promised and What Isn't

Guaranteed: ordering within one partition

All messages within a single partition are strictly ordered by offset. If order-AAA (offset 0) was written before order-GGG (offset 1), every consumer that reads partition-0 will always see order-AAA first. Always. This is an iron-clad guarantee enforced by the append-only log structure and by Kafka's replication protocol.

Not guaranteed: ordering across partitions

order-AAA (partition-0) and order-BBB (partition-1) were written in that order, but are handled by different consumer threads with no coordination. There's no global ordering. If your business logic requires global ordering across all messages, you must use 1 partition — but that eliminates all parallelism. Design your keys to avoid this requirement.

FoodFlash design decisionWe use orderId as the message key for order.created and order.status. Kafka hashes the key: partition = hash("order-AAA") % 6 = 2. All events for order-AAA always land on partition-2. The consumer reading partition-2 sees order-AAA's entire lifecycle in exact order: PENDING → CONFIRMED → PREPARING → PICKED_UP → DELIVERED. This is ordering where it matters, without sacrificing global parallelism.
Chapter 5 — Core Mechanics

Replication — RF=3 in Complete Detail

Replication Factor 3 means every message you write is stored on three separate broker disks simultaneously. One broker is the "leader" for each partition and handles all reads and writes. The other two are "followers" — they continuously replicate every message from the leader and stand ready to take over instantly the moment the leader dies. This is how Kafka guarantees zero data loss even when machines fail.

The Complete Write Path — What Happens When Spring Boot Publishes a Message

1
Spring Boot calls producer.send()
The Kafka producer client (inside your Spring Boot jar) looks up its cached metadata: "Who is the leader for order.created partition-0?" The answer is kafka1. The producer opens a TCP connection to kafka1:29092 and sends the message. The message payload is: key=orderId, value=JSON, headers=timestamp+traceId.
2
kafka1 appends to its local log file
kafka1 writes the message to its active segment file: /var/kafka-logs/order.created-0/00002000.log, assigning it offset 2001. This is a sequential disk write — extremely fast (microseconds) because modern SSDs and HDDs are optimized for sequential I/O.
3
Followers fetch the new message (asynchronously)
kafka2 and kafka3 are followers for partition-0. They each run a "replication fetch" loop — continuously asking the leader: "Give me all messages after offset 2000." kafka1 responds with the new offset 2001 message. Both kafka2 and kafka3 write it to their own disks. This happens independently and continuously, regardless of whether anyone is reading the topic.
4
ISR (In-Sync Replicas) confirm — what acks=all means
The In-Sync Replica set (ISR) is the list of follower brokers that are caught up within a configurable lag threshold. With acks=all (which we use for order.created), kafka1 does NOT acknowledge the producer until every broker in the ISR has confirmed they've persisted offset 2001. So the producer's producer.send() call blocks until all 3 brokers confirm. This adds ~5–10ms latency but guarantees that even if kafka1 crashes immediately after sending the ack, the message is already on kafka2 and kafka3.
✓
Producer receives "success" — message on 3 disks
Spring Boot's producer.send() returns. The message is durably stored on kafka1, kafka2, and kafka3. The cluster can lose any one of these machines entirely and suffer zero data loss. This is what makes Kafka production-grade.

Producers, Keys & Message Routing

A producer publishes messages to a Kafka topic. The message key is the most consequential decision a producer makes — it determines which partition the message lands in, which determines ordering, load distribution, and which consumer instance processes it. Get the key wrong and you get hot partitions, broken ordering, and wasted parallelism.

How Partition Selection Works

When a producer sends a message, Kafka must decide which of the 6 partitions to put it in. The logic is:

// If message has a key:
partition = murmur2_hash(key) % numPartitions
// murmur2 is a fast, deterministic hash function
// Same key → same hash → same partition, always, forever
// "order-AAA" always maps to partition-2 (for example)
// Even after broker restarts, partition count changes would break this
// (which is why you don't change partition count on live topics)

// If message has no key:
// Kafka uses a "sticky partitioner" (Kafka 2.4+) — batches messages to one
// partition until the batch is full, then switches. Old behavior was pure round-robin.
// Either way: no ordering guarantee, but even load distribution.

Chapter 7 — Core Mechanics

Consumer Groups — How Independent Readers Work

A consumer group is a named team of consumer instances that collaborate to read a topic. Each partition is assigned to exactly one instance within the group at any time — so instances share the work without duplicating it. Multiple independent groups can read the same topic simultaneously with no coordination and no interference with each other.

The Two Rules That Govern Everything

Rule 1 — Within one consumer group: each partition is exclusively owned by exactly one consumer instance at any moment. Two instances in the same group cannot both process messages from the same partition simultaneously. Kafka enforces this at the protocol level — it's not something you manage in code.

Rule 2 — Across different consumer groups: every group gets a completely independent view of the topic. They each track their own position independently. One group's position, speed, or failures have zero effect on any other group. The same message is delivered to every group.

Why "Two Consumers Both Read offset 1001" Is Possible

The rule is "one partition per consumer per group." Different groups each have their own independent assignment. So order-service-group's instance-1 owns partition-0 within order-service-group. notification-group's instance-1 also owns partition-0 within notification-group. They don't share — each group independently tracks its position in __consumer_offsets under its own group ID key. No coordination, no shared state, no interference.

Idle Consumers — The Hard Ceiling

You can never benefit from more consumer instances than partitions. The 7th instance in a 6-partition topic gets zero partition assignments and sits idle forever, consuming memory and CPU for nothing. This is a hard limit enforced by Kafka — a partition cannot be split between two consumers in the same group. Design your partition count with your expected maximum parallelism in mind.

Chapter 8 — Core Mechanics

Offsets — Bookmarks, Commits & Replay

An offset is the address of a message within a partition. Consumer groups track their reading position by storing their current offset in an internal Kafka topic called __consumer_offsets. This design — positions stored inside Kafka itself — is what enables independent consumers, crash recovery, replay, and new service catchup. It's also why resetting consumer positions requires stopping the service first.

__consumer_offsets — What It Is and Why It Exists

In Kafka's earliest versions, consumer offsets were stored in Zookeeper. This turned out to be a bottleneck — Zookeeper is optimized for rare configuration reads, not the high-frequency small writes that offset commits generate (potentially thousands per second across a large cluster). Since Kafka 0.9 (2015), offsets are stored in an internal Kafka topic: __consumer_offsets.

This topic has 50 partitions (so offset commits can be distributed across brokers) and RF=3 (so offset data survives broker failures). When a consumer commits its position, it writes a record to this topic:

// Record written to __consumer_offsets when consumer commits:
key:   group_id="order-service-group" + topic="order.created" + partition=0
value: offset=1002  metadata="processed at 2025-01-15T14:32:11"  timestamp=1736944331000

// This means: "order-service-group has processed everything up to and including
// offset 1001 in partition-0 of order.created.
// Next time this group reads partition-0, start from offset 1002."

Because __consumer_offsets is itself a Kafka topic with RF=3, your consumer positions survive any single broker failure. Even if kafka1 dies, the offset record is on kafka2 and kafka3.

Chapter 9 — Advanced L5

When a Broker Dies — Full Walkthrough

You asked exactly the right question: "If kafka1 dies, it was leader for P0 and P3. Do those partitions go dark until kafka1 comes back? What happens to all the messages going to P0 and P3 while kafka1 is down?" This chapter answers that completely — with the exact sequence of events and the reason zero data is lost.

The Critical Misunderstanding — Clarified First

When we say "kafka1 is the leader for P0 and P3," we mean kafka1 is currently responsible for handling reads and writes for those partitions. It does NOT mean kafka1 is the only place where P0 and P3 data exists.

Because RF=3, every message ever written to P0 is already on kafka1 AND kafka2 AND kafka3. All three brokers have identical copies of P0's data (up to the replication lag, which with acks=all is zero). The "leader" label is just a routing designation — who handles traffic. The moment the leader dies, the routing label can be moved to any follower that has all the data. And they do — because they've been continuously replicating in real-time.

Analogy: Three identical textbooks, one assigned to be the "primary" reference. If the primary is lost, you immediately promote one of the other two — which have identical content. No information was lost. The only thing that changed was which book you point to.

The Exact Timeline When kafka1 Dies at 3:00pm

💥
T=0s — kafka1 process crashes (OOM, hardware failure, docker kill)
The kafka1 container is dead. It was leading P0 and P3 across all topics. kafka2 and kafka3 are still running, each holding complete replica copies of P0 and P3. These replicas are not "stale backups" — they were continuously receiving every single message kafka1 received (with acks=all, they were fully in sync before any message was acknowledged).
5s
T=5s — Zookeeper detects the missing heartbeat
kafka1 was sending a heartbeat to Zookeeper every 2 seconds. Zookeeper waits for the configured session timeout (default: 6 seconds). At 5s of silence, Zookeeper declares the session expired and emits a "broker 1 is dead" event to all remaining brokers. kafka2 and kafka3 receive this notification.
6s
T=6s — Kafka Controller checks the ISR for P0 and P3
One broker in the cluster acts as the "Controller" — elected once at cluster startup. The Controller is responsible for managing leader elections. It checks the ISR (In-Sync Replica set) for partition-0: the ISR was [kafka1, kafka2, kafka3]. kafka1 is dead, so eligible candidates are kafka2 and kafka3 — both have complete data. The Controller picks kafka2 as the new leader for P0. For partition-3, it picks kafka3.
7s
T=7s — kafka2 becomes leader for P0; kafka3 becomes leader for P3
kafka2 updates its internal state: "I am now the leader for P0." kafka3 updates: "I am now the leader for P3." Zookeeper is updated with the new leader assignments. The cluster metadata is propagated. Total time from crash to new leader: about 7 seconds.
9s
T=9s — Producer and consumer clients automatically reroute
The Kafka producer client library (inside your Spring Boot jar) has built-in retry and metadata refresh logic. When it tries to send a message to kafka1 (the old leader for P0) and gets a connection error or a "not a leader" error, it automatically re-fetches cluster metadata from any available broker, discovers kafka2 is now the leader for P0, and starts sending there. No code changes. No service restart. The retry is transparent.
10s
T=10s — Cluster fully operational with 2 brokers
All 6 partitions have live leaders: P0→kafka2, P1→kafka2, P2→kafka3, P3→kafka3, P4→kafka2, P5→kafka3. kafka2 and kafka3 are now each leading 3 partitions (they took over kafka1's partitions). All producers and consumers have rerouted. Zero data was lost because acks=all guaranteed everything was on all 3 disks before any message was acknowledged.

What Happens to Messages Produced to P0 During the Outage

This is the specific scenario you were worried about: "while kafka1 is down, producers trying to write to P0... where do those messages go?"

After election (T=10s onward) — fully transparent

Once kafka2 is elected leader for P0 (takes ~7-10 seconds), the producer client auto-discovers this and sends P0 messages to kafka2. Consumers reading P0 now read from kafka2. Everything works identically to before — kafka2 just happens to be answering now instead of kafka1. The message stream is uninterrupted.

During election (T=0s → T=10s) — brief retry period

During these ~10 seconds, producers trying to write to P0 get connection errors or "not a leader" responses. The producer client has built-in retry logic: it retries up to retries=Integer.MAX_VALUE times with exponential backoff. With delivery.timeout.ms=120000 (2 minutes default), the producer keeps retrying until a new leader is elected and the message is delivered. From the Spring Boot perspective, the send() call blocks a bit longer than usual, but ultimately succeeds. No message is lost.

The bottom line: P0 and P3 don't "go dark." They are briefly unavailable for writes (~7-10 seconds) during leader election, during which producers retry. After election, kafka2 and kafka3 fully handle those partitions with identical data. The gap is invisible to your application code because the Kafka client libraries handle retries transparently.

When kafka1 Comes Back — The Rejoin Process

This is equally important to understand. When kafka1 restarts, it does NOT immediately reclaim P0 and P3 leadership. Here's why and what actually happens:

1
kafka1 starts up and registers with Zookeeper
kafka1 announces itself: "I'm back, I'm broker 1." But the cluster's current state is: kafka2 leads P0 (and has been receiving all P0 writes during kafka1's absence). kafka1's local log for P0 is behind — it's missing everything written while it was dead.
2
kafka1 joins as follower for P0 and P3 — not immediately as leader
kafka1 cannot be promoted to leader for P0 until it catches up with kafka2 (the current leader). So it joins as a follower: it starts fetching all the messages it missed from kafka2 while it was dead. This is the same replication fetch loop that normally keeps followers in sync.
3
kafka1 catches up and re-enters the ISR
Once kafka1 has replicated all the messages it missed (could take seconds to minutes depending on how long it was dead and how much traffic there was), it is back in the ISR for P0 and P3. It's now a fully in-sync replica again.
4
Preferred leader election restores kafka1 as leader for P0, P3
With auto.leader.rebalance.enable=true (default), the Controller periodically runs preferred leader election. kafka1 is the "preferred leader" for P0 and P3 (it was originally assigned those). Once kafka1 is fully in-sync, the Controller moves leadership back to kafka1. This happens during a quiet period to minimize disruption. kafka2 smoothly transitions back to being a follower for P0.

"When kafka1 dies, P0 and P3 aren't lost because RF=3 means all data was already on kafka2 and kafka3 — followers replicate in real-time, and with acks=all, every acknowledged message was confirmed on all three disks before the producer received success. Zookeeper detects the death via heartbeat timeout in about 5-6 seconds. The Kafka Controller then elects a new leader from the ISR for each affected partition — kafka2 takes P0, kafka3 takes P3 — in about 1-2 more seconds. Producer and consumer clients automatically reroute by re-fetching cluster metadata. During the ~7-10 second election window, producers retry automatically and no messages are lost. When kafka1 revives, it rejoins as a follower, catches up on missed messages, re-enters the ISR, and preferred leader election eventually returns P0/P3 leadership to it. Total visible impact: a brief latency spike in the 10-second window, zero data loss."

Chapter 10 — Advanced L5

Storage, Segments & Retention

Kafka messages are stored on broker disk as segment files within partition directories. A background thread on each broker periodically scans these files and deletes segments that have exceeded the retention threshold. This deletion is based purely on time or size — consumer reads have absolutely no effect on when messages are deleted.

How Segment Files Work

Each partition is not one giant file — it's a directory of rolling segment files. Kafka splits messages into segments because you can't efficiently delete from the middle of a large file. The active segment receives new messages. Sealed segments are immutable and eligible for deletion.

# Inside kafka1, partition-0 of order.created:
/var/kafka-logs/order.created-0/
  00000000000000000000.log    # messages offset 0–999 (sealed, 7 days old)
  00000000000000000000.index  # offset→byte_position index
  00000000000001000000.log    # messages offset 1000–1999 (sealed, 5 days old)
  00000000000001000000.index
  00000000000002000000.log    # messages offset 2000–present (ACTIVE — never deleted while open)
  00000000000002000000.index
  leader-epoch-checkpoint     # tracks leader term changes for correctness

The Deletion Logic — Exactly How It Works

The log cleaner thread runs on every broker every 5 minutes (configurable). For each sealed segment, it checks:

# Pseudocode for the log cleaner's decision:
for partition in all_partitions:
    for segment in sealed_segments(partition):
        newest_message_timestamp = segment.last_record_timestamp
        age = current_time - newest_message_timestamp
        
        if age > retention_ms:           # 7 days = 604,800,000ms
            delete(segment.log_file)
            delete(segment.index_file)
            delete(segment.timeindex_file)
        # else: keep the entire segment, even if first message is ancient

    # Active segment: NEVER deleted regardless of age
    # Consumer offsets: NEVER consulted. Deletion doesn't care who read what.

The key insight: deletion happens at segment granularity, not at message granularity. If a segment contains messages from day 1 to day 7, the entire segment is kept until the newest message in it exceeds the retention period. This means retention is not precise — it's precise to the nearest segment boundary (which is configurable but defaults to 1GB or 7 days of data).

Consumer reads do not prevent deletion. Kafka has no concept of "wait until all consumers read before deleting." If you have a consumer group that falls behind by more than the retention window, those messages will be deleted while the consumer is still behind. When the consumer tries to read its last committed offset, Kafka responds with OffsetOutOfRangeException — the data at that offset no longer exists. Your code must handle this by resetting to the earliest available offset and logging that data was lost for investigation.

Rebalancing — Every Trigger Explained

A rebalance is when Kafka redistributes which partitions are assigned to which consumer instances within a group. This happens when the group's membership changes. During a rebalance, all consumption pauses — no consumer in the group reads any messages until new assignments are complete. This "stop the world" behavior is what makes rebalancing a production concern.

Chapter 12 — Advanced L5

Delivery Guarantees — In Depth

What happens when your consumer crashes between reading a message and committing the offset? The answer depends on which delivery guarantee you've configured. There are exactly three options, each a deliberate trade-off between safety, performance, and complexity. Understanding when each is appropriate separates senior engineers from juniors.

The Core Tension

The fundamental problem: reading a message and recording "I've read it" are two separate operations. A crash between them creates ambiguity. You can resolve this ambiguity in favor of "never lose a message" (risking duplicates) or "never duplicate a message" (risking loss). Exactly-once semantics eliminate the trade-off via transactions — at a performance cost.

📤
At Most Once
Commit the offset before processing. If crash happens after commit but before processing completes: the message is never retried. Silently lost.
  • No duplicate processing, ever
  • Messages can be permanently lost
  • Fastest — no retry overhead
  • Best for: metrics, logs, analytics where approximation is acceptable
  • FoodFlash: chat.typing (loss = nobody sees "typing" — fine)
🔄
At Least Once
Commit the offset after processing. If crash after processing but before commit: message is reprocessed. Duplicates are possible but no message is lost.
  • No message loss — everything eventually processed
  • Duplicates possible — handle in your code
  • Requires idempotent processing logic
  • Industry default — most production systems use this
  • FoodFlash: order.status, chat.message (dedup by message_id)
🎯
Exactly Once
Kafka transactions make read, process, and offset-commit atomic. Either all happen or none do. No loss, no duplicates, ever.
  • Perfect semantics — no loss, no duplicate
  • ~30% throughput reduction vs at-least-once
  • Significant configuration complexity
  • Only for high-stakes financial operations
  • FoodFlash: order.created (duplicate order = charged twice)

At Least Once — The Crash Scenario Step by Step

1
Consumer reads offset 1001 from partition-0
Spring Boot @KafkaListener method receives the message. The offset has NOT been committed yet — __consumer_offsets still says the group's last position is 1000. Kafka will deliver 1001 again if the consumer restarts now.
2
Consumer processes — INSERT INTO orders...
The order is successfully written to PostgreSQL. The database row exists.
💥
JVM crash — before commitSync() is called
The process dies. __consumer_offsets was never updated. The group's committed position is still 1000 — meaning "I've processed everything through offset 1000. Give me 1001 next."
!
Consumer restarts — reads offset 1001 AGAIN
The restarted consumer reads __consumer_offsets and sees: "last committed = 1000." It requests offset 1001 from Kafka. Kafka delivers offset 1001 — the same message the previous instance already processed and wrote to PostgreSQL.
✓
Fix: idempotent insert with ON CONFLICT DO NOTHING
Use the orderId as the database primary key. The second INSERT hits the UNIQUE constraint and is silently ignored. No duplicate order. This is "idempotent processing" — processing the same message twice produces the same result as processing it once. Design every consumer with this property.
// Bad — duplicates silently created on retry:
jdbcTemplate.update("INSERT INTO orders (id, user_id, ...) VALUES (?, ?, ...)", ...);

// Good — idempotent, safe for at-least-once:
jdbcTemplate.update(
    "INSERT INTO orders (id, user_id, ...) VALUES (?, ?, ...) ON CONFLICT (id) DO NOTHING", ...
);

Thread Safety — Why It's Architecturally Guaranteed

You might wonder: "If my Spring Boot service has 6 threads all consuming from order.created, can two threads race on the same partition's offset?" The answer is no — and it's guaranteed by architecture, not by your code. Partition ownership is the mutex.

The Question

Spring Boot with spring.kafka.listener.concurrency=6 creates 6 consumer threads. All 6 are in the same consumer group. If partition-0 has message at offset 1001 ready, don't multiple threads try to grab it simultaneously? Wouldn't they race on the offset commit?

Why It Cannot Happen — Partition Ownership

Kafka assigns each partition to exactly one consumer instance (thread) within the group. With 6 threads and 6 partitions, the assignment is:

Thread-1 → partition-0  (exclusive ownership: only thread-1 reads P0)
Thread-2 → partition-1  (exclusive ownership: only thread-2 reads P1)
Thread-3 → partition-2  (exclusive ownership)
Thread-4 → partition-3  (exclusive ownership)
Thread-5 → partition-4  (exclusive ownership)
Thread-6 → partition-5  (exclusive ownership)

Thread-1 reads P0's offset 1001, processes it, commits offset 1002.
NOBODY ELSE touches P0's offset entry in __consumer_offsets.
Thread-2 is doing the same thing for P1, independently, simultaneously.
There is NO shared mutable state between threads.
The offset commit from Thread-1 and Thread-2 go to DIFFERENT partitions
  of __consumer_offsets — they don't even contend on the same internal partition.

The partition assignment itself is the mutex. This is an architectural guarantee from Kafka's protocol — not something you implement or configure. Your listener code is called by one thread at a time per partition, sequentially. You write plain sequential code with no locks needed.

The Implication for Your Code

@KafkaListener(topics = "order.created", groupId = "order-service-group")
public void handleOrder(ConsumerRecord<String, String> record) {
    // This method is called by Thread-1 for partition-0 messages,
    // Thread-2 for partition-1 messages, etc.
    // Thread-1 and Thread-2 call this method simultaneously
    // but for DIFFERENT records from DIFFERENT partitions.
    // They never share offset state.
    //
    // You do NOT need: synchronized blocks, ReentrantLock,
    //   AtomicReference, ConcurrentHashMap (for the Kafka position itself).
    //
    // You DO still need thread-safety for: any shared application state
    //   you maintain (e.g., a shared in-memory counter across all partitions).
    //   But that's your application's problem, not Kafka's.
    
    Order order = objectMapper.readValue(record.value(), Order.class);
    orderRepository.save(order); // plain code, no synchronization needed
}

"Kafka guarantees thread safety through partition ownership — within a consumer group, each partition is exclusively owned by exactly one consumer thread at any time. With concurrency=6 and 6 partitions, each thread has exclusive ownership of one partition. Thread-1 reads P0's messages and commits P0's offset. Thread-2 does the same for P1. They never share partition assignments, so there's no race condition on offset commits. The offset commit from Thread-1 writes to a specific partition of __consumer_offsets keyed by (group, topic, partition=0) — a completely different key than Thread-2's commit for partition=1. No lock needed. Write plain sequential code in your listener and Kafka's protocol handles the rest."
