OS, Kernel & Processes

The foundation everything sits on. You can't understand Docker without first understanding what a kernel is and what a process actually means.

what is the kernel

Your Operating System (macOS, Windows, Linux) has two layers. The part you see — apps, desktop — and the part you never see: the kernel. The kernel is the only software that speaks directly to physical hardware. Every single app must ask the kernel for whatever it needs. No app ever touches hardware directly.

what is a process

When you open Zomato, the OS loads the app's code from disk into RAM and starts executing it. That running instance is called a process. The kernel gives it a PID (process ID), carves out a private slice of RAM, schedules CPU time — and enforces that it cannot see into Chrome's memory or touch Spotify's files.

process vs thread

A process is a walled apartment with its own RAM. A thread is a worker inside that apartment. All threads in the same process share the same RAM — fast to communicate, but dangerous (race conditions). Threads in different processes cannot touch each other at all.

Your thread math — corrected: 32 cores = 32 threads running at the exact same instant. But you can create thousands of threads — the kernel rapidly switches which one runs on which core every ~1ms (context switching). So 10 processes × 32 threads = 320 threads exist in memory, only 32 execute at any given moment. The rest wait their turn.
🎯 Interview Q — L5 / Staffshow answer ▾
"Your Node.js service has 1 CPU core allocated and handles 500 concurrent requests. How is that possible with a single thread?"
Event loop + non-blocking I/O. Node never blocks waiting for DB/network. When a request needs a DB query, Node registers a callback and immediately moves to the next request. The OS signals Node when DB responds. 500 "concurrent" requests are 500 requests in various I/O-waiting stages — one thread handles whoever is ready at each tick. Great for I/O-heavy work; terrible for CPU-heavy (one heavy computation blocks the whole loop).

What Docker Actually Is

VMs vs containers side-by-side, the shared kernel model, images vs containers, and why "works on my machine" is finally solved.

VMs vs containers — the architecture difference
Common misconception: containers are NOT more secure than VMs. The shared kernel means a kernel exploit in any container can compromise the host. VMs require breaking the hypervisor — a far harder target.
image vs container — the most important distinction
local laptop → prod EC2 — same image, identical result
🎯 Interview Q — Seniorshow answer ▾
"App works on your laptop but crashes on prod EC2 immediately. Same image. What are the possible causes?"
1. Missing env vars. Secrets on laptop (via .env) aren't baked into images. Fix: inject via K8s Secret or AWS Secrets Manager.

2. Architecture mismatch. Built on Apple Silicon (ARM), running on x86 EC2. Fix: build with --platform linux/amd64.

3. OOMKill. EC2 has less RAM. Check docker inspect for OOMKilled:true, exit code 137.

Debug sequence: docker logs <container_id> → docker inspect for OOMKilled → check env vars → check arch.

Images, Layers & Builds

How images are structured as layers, why cache order is everything, the delete trap, and multi-stage builds.

image layers — how OverlayFS stacks them

A Docker image is not a single file. It is a stack of read-only layers, each one a diff from the previous — exactly like Git commits. Linux's OverlayFS merges them into a single view. Each RUN/COPY/ADD in your Dockerfile creates a new layer.

the cache ordering trick — 8 min build → 30 sec
❌ BadCOPY all code first
COPY . . # cache miss every commit RUN npm ci # reruns every build = 3 min
npm install reruns on every single code change because COPY . . always changes.
✅ GoodPackage files first
COPY package*.json ./ # stable layer RUN npm ci # cached 99% of time COPY . . # code here
npm install only reruns when package.json changes. Code changes = skip directly to COPY.
The delete trap: Add a 500MB file in one RUN, delete it in the next RUN — image still 500MB heavier. The file exists in layer N. OverlayFS marks it deleted in layer N+1 but doesn't remove it from the previous layer. Fix: everything in a single RUN command.
multi-stage builds — the image diet

To compile code you need compilers. To run code you need only the binary. Multi-stage builds let you use multiple FROM stages — compile in a fat stage, copy only the output to a minimal final stage.

🎯 Interview Q — Staff levelshow answer ▾
"Your Go microservice image is 1.1GB. Walk me through getting it under 20MB."
Step 1 — Multi-stage build: compile in golang:alpine, copy only the binary.
Step 2 — Static binary: CGO_ENABLED=0 GOOS=linux gives a statically-linked binary, no glibc dependency.
Step 3 — Minimal base: distroless/static (2MB) or scratch (0MB).
Result: binary ~8MB + base ~2MB = ~10MB.
Bonus: -ldflags="-s -w" strips debug symbols (30% smaller).

Namespaces & cgroups

The two Linux kernel primitives that make containers real. Docker does nothing more than configure these correctly.

namespaces — making a process think it is alone

A namespace gives a process a private view of a system resource. The resource exists on the host, but each namespace sees its own isolated copy. Docker creates 7 namespaces per container at startup.

user namespace is the security holy grail — but NOT enabled by default. With it: root inside container maps to unprivileged UID 100000 on host. Attacker escapes container — they're nobody on the host. Without it: root inside = root on host. Enable rootless Docker to get this.
cgroups — resource limits the kernel enforces
the runtime stack — what runs when you type docker run
🎯 Interview Q — Staff · very common at Ubershow answer ▾
"p99 latency spikes to 800ms during peak. No OOMKill. CPU dashboards show 30% average. What's happening?"
CPU throttling. Container hits its cgroup CPU quota and gets paused by the kernel. Dashboards show time-window averages — which look low even during burst throttles.

Confirm: cat /sys/fs/cgroup/cpu/cpu.stat — check throttled_time. If non-zero and growing, that's it.

Fix: raise --cpus limit, or switch to --cpu-shares (soft limit, allows bursting when host has spare). In Kubernetes: resources.limits.cpu set too low is the most common cause of mystery latency at Uber scale.

Networking & Storage

How containers find each other, the DNS trap every engineer hits once, and why data disappears when containers stop.

bridge networking — the physical path packets take
ModeHow it worksPerformanceUse case
bridgeVirtual switch + veth pairs + NAT~2-5% NAT overheadDefault — most containers
hostShares host's network namespace directlyZero overhead — native speedLatency-sensitive services
overlayVXLAN tunnel across physical network~10-15% overheadContainers on different hosts
noneOnly loopback — fully isolatedN/ABatch jobs, security-critical
volumes — why data vanishes and how to fix it

Writes inside a container go into the container's writable layer on top of image layers. When the container is deleted, that layer is gone. Databases, uploads, logs — all lost. A volume mounts storage from outside the container layer — writes go to the host disk, survive container deletion.

🎯 Interview Q — Seniorshow answer ▾
"High-frequency trading service in Docker shows 2ms higher p99 latency than the same binary on the host. What causes this?"
Bridge network's NAT path: each packet traverses the veth pair, docker0 virtual switch, and iptables NAT rules — microseconds per packet that compound to 2ms at HFT frequency.

Fix: --network host. Container uses host's network interface directly. Zero NAT overhead. Container port = host port (no mapping needed). Downside: two containers can't share the same port number.

Security & Hardening

Linux capabilities, seccomp, the SIGTERM trap, and health checks. What it takes to run containers safely at Uber scale.

the fundamental limit
Containers share the kernel. A kernel-level exploit in any container can compromise the host. Everything below reduces blast radius — nothing eliminates this root risk. VMs remain fundamentally stronger for hostile workloads.
linux capabilities — root split into 40 fine-grained permissions

Old Linux: you're either root (do anything) or not (very limited). Modern Linux splits root into ~40 individual capabilities. Docker containers get a subset by default. The move: drop all, add only what your app actually needs.

CapabilityWhat it allowsNeed it?
CAP_NET_BIND_SERVICEBind to ports below 1024Only if binding port 80/443
CAP_SYS_PTRACEDebug processes with strace/gdbNever in prod
CAP_SYS_ADMIN"God mode" — mount, change namespacesNever. Red flag if requested.
CAP_NET_ADMINModify network interfaces, iptablesOnly for network-level tools
# Hardened container — production standard docker run \ --cap-drop=ALL \ # remove every capability --cap-add=NET_BIND_SERVICE \ # add back only what's needed --security-opt no-new-privileges \ # cannot sudo or setuid escalate --read-only \ # immutable filesystem --tmpfs /tmp:size=50m \ # writable scratch in RAM --user 1000:1000 \ # non-root user myapp
The #1 Docker security mistake: -v /var/run/docker.sock:/var/run/docker.sock. The Docker socket gives full control of dockerd — spin up privileged containers, mount host filesystem. It hands the container root access to your entire host.
the SIGTERM trap — why rolling deploys drop requests
health checks — running ≠ ready

A container can be "running" (process alive) but completely broken (DB failed, stuck in a loop). Without a health check the orchestrator thinks it's fine and keeps sending traffic. A health check tells K8s: call this endpoint every 30s — 3 failures = restart and stop routing.

HEALTHCHECK --interval=30s --timeout=5s --start-period=15s --retries=3 \ CMD curl -f http://localhost:8080/health || exit 1 # /health must return 200 only when truly ready: # ✓ database connection working # ✓ cache loaded # NOT just "process is running"
🎯 Interview Q — Staff / Principalshow answer ▾
"Attacker gets RCE in a container running as root. Which isolation mechanisms prevent host takeover? Which don't help?"
What helps: mnt namespace (can't see host filesystem), net namespace (can't sniff host traffic), seccomp (dangerous syscalls blocked), AppArmor/SELinux MAC policies, distroless image (no shell or tools to use post-RCE).

What doesn't help: Running as root = all default capabilities. Without user namespaces, root inside = root on host. Kernel vulnerability = all namespace isolation breaks — shared kernel is the fundamental limit.

Full hardening: non-root + user namespaces + seccomp + cap-drop=ALL + distroless + read-only filesystem. Even then a kernel 0-day beats everything.

CI/CD & Deployment

Build pipelines, image tagging, BuildKit cache mounts. What 100,000 deploys per week looks like at Uber.

Uber context: 4,500 microservices on K8s (migrated from Mesos July 2024). 100,000+ deploys/week. The deployment pipeline design IS the system design question at staff level.
build once, deploy many — the golden rule
Never rebuild for different environments. Never use :latest in prod. Tag with git commit SHA. Same image SHA promoted through dev → staging → prod by retagging. Same SHA = same code = provably identical behaviour everywhere. Rollback = re-tag to previous SHA. 30 seconds, no rebuild.
the full pipeline — 5 stages
buildkit cache mounts — the biggest practical speedup
# Without — downloads everything every build (~3 min) RUN pip install -r requirements.txt # With cache mount — reuses downloads (~15 sec) · NEVER in image layer RUN --mount=type=cache,target=/root/.cache/pip \ pip install -r requirements.txt # Secret mount — token available at build time, NEVER appears in any layer # (ARG/ENV for secrets = visible in docker history forever = don't do it) RUN --mount=type=secret,id=gh_token \ pip install --index-url $(cat /run/secrets/gh_token) private-pkg
🎯 System design Q — Staff level (Uber)show answer ▾
"Design a container image build and promotion pipeline for 4,500 microservices, 100,000 deploys/week."
Build: Kaniko in K8s pods (no privileged access). BuildKit cache mounts on CI runner. One build per commit SHA. Parallel builds for independent services.

Registry: At this scale central pull saturates bandwidth. P2P registry (Uber open-sourced Kraken) — hosts seed image layers to neighbours after first pull.

Security gate: Trivy CVE scan + cosign signing. Prod registry only accepts signed images. Block on CRITICAL.

Promote: Same sha256 digest through all envs. Config via K8s ConfigMap/Secret — never baked into image.

Rollback: kubectl rollout undo or re-tag to previous SHA. 30 seconds. Keep last 10 versions in registry at all times.

Quick Revision

Everything Uber interviews will test — key facts, common traps, and one-liner answers. Read this the day before your interview.

kernel & process fundamentals
🧱 OS & Kernel
Kernel is the only software that talks to hardware directly. Every app — Chrome, Spotify, Zomato — must ask the kernel for CPU, RAM, disk, and network.
macOS / Windows / Linux = kernel + apps on top. The kernel IS the core OS. The desktop GUI is just another app.
Process = a running instance of a program. The kernel gives it its own PID, a private RAM slice, and CPU time.
Processes are isolated by the kernel — Chrome cannot read Zomato's memory. One process crashing doesn't kill others.
Thread = a worker inside a process. All threads in the same process share the same RAM — fast to communicate, but race conditions are possible.
32 cores = 32 threads running simultaneously at any instant. Thousands of threads can exist in RAM — the kernel rotates them onto cores every ~1ms (context switching).
🐳 Docker Basics
Image = frozen blueprint on disk. Container = live running process created from that image. Same image → run 10 times → 10 containers.
Containers share the host kernel. VMs have their own. Containers boot in ~200ms vs ~45s for VMs.
Container is NOT more secure than a VM. Shared kernel = shared blast radius. A kernel exploit in any container can hit the host.
Image layers are content-addressed by SHA256. Unchanged layers reuse cache instantly — no rebuild, no download.
Once a layer changes, all layers below it must rebuild. Put stable things first: base OS → system tools → npm deps → source code.
Deleting a file in the next RUN still bloats the image — it exists in the previous layer. Fix: everything in one RUN command.
internals — namespaces & cgroups
🔬 Namespaces (7 types)
pid — container gets its own process tree. Container PID 1 ≠ host PID 1.
net — own eth0, ports, routing, iptables. Two containers can both claim port 8080 internally.
mnt — own filesystem from the image. Host /home is invisible to the container.
user — root inside container maps to UID 100000 on host. Not enabled by default — need rootless Docker.
K8s Pod: containers in the same Pod share the net namespace — they have the same IP and talk via localhost.
K8s dropped dockerd in v1.24. kubelet now talks to containerd directly. Your images still work — OCI format is identical.
📊 cgroups
Memory limit hit → OOMKill. Container exits code 137. Immediate death, no cleanup. Check: docker inspect --format '{{.State.OOMKilled}}'
CPU limit hit → Throttling, not death. Kernel pauses the process until the next quota window. App slows, doesn't die.
Dashboard shows CPU averages — throttling spikes during bursts are invisible to averages. Check: cpu.stat → throttled_time
K8s: requests = scheduling guarantee (what node needs to fit the pod). limits = hard cgroup ceiling (enforcement).
CPU throttle + low average CPU on dashboard = the most common mystery latency bug at Uber scale.
networking traps
🌐 The DNS Trap
Default bridge = no DNS. connect("kafka") fails — containers only know each other by IP, which changes on restart.
User-defined bridge = Docker embeds DNS at 127.0.0.11. Container names resolve automatically — no IPs needed.
Docker Compose always creates a user-defined network — that's exactly why service names just work.
host mode: zero NAT overhead. Container port = host port. Best for latency-sensitive services.
overlay: VXLAN tunnel across physical hosts. ~10-15% overhead. Used by K8s multi-node networking.
💾 Storage
Writes inside a container go into its writable layer — destroyed on docker rm. Database data, uploads, logs — all lost.
Named volume: Docker manages the path. Survives container deletion. Use for databases and any persistent state.
Bind mount: any host path mapped into container. Perfect for local dev hot-reload. Bad for prod (host-path dependent).
tmpfs: RAM only, never written to disk. Use for secrets that must never touch disk, or temp scratch space.
Volumes bypass OverlayFS — better I/O performance than writing inside the container layer.
production traps
🔒 Security must-knows
Never mount /var/run/docker.sock into a container — it gives full root access to the host daemon.
--cap-drop=ALL then add back only what the service actually needs. Most web services need zero capabilities.
Distroless base image: no shell, no apt, no curl. Attacker gets RCE but has nothing to work with.
Secrets in ARG or ENV are visible in docker history forever. Use --mount=type=secret in BuildKit instead.
A kernel exploit breaks all container isolation. Shared kernel = shared risk ceiling — VMs remain stronger for hostile workloads.
🚨 The SIGTERM Trap
Shell form ENTRYPOINT "./server": shell becomes PID1, SIGTERM never reaches your server. After 10s → SIGKILL → requests dropped.
Exec form ENTRYPOINT ["./server"]: your server IS PID1, receives SIGTERM directly, can drain connections and exit cleanly.
Use tini as PID1 if your app spawns child processes — it forwards signals and reaps zombies automatically.
K8s: preStop hook + sleep 5 gives the load balancer time to drain before SIGTERM is sent. Pair with terminationGracePeriodSeconds.
CI/CD & deployment must-knows
🚀 Deployment rules
Never use :latest in production. Tag with git commit SHA. Rollback = retag to the previous SHA, not a rebuild.
Build once per SHA. Promote the same image through dev → staging → prod by retagging. Never rebuild for different environments.
Config (env vars, secrets) is injected by K8s at runtime. Never bake config into the image.
BuildKit cache mounts: pip/npm package cache persists between CI builds without ever entering an image layer.
Kaniko / Buildah for CI builds: daemonless, no privileged pods, safer than DinD (Docker-in-Docker).
⚡ Multi-stage builds
Go example: compile in golang:alpine (~350MB), copy only the binary to distroless/static (~2MB). Final image: ~10MB.
CGO_ENABLED=0 produces a statically linked binary — no glibc dependency, runs in distroless or scratch.
Cache order: COPY package.json → RUN npm install → COPY . . — npm install only reruns when dependencies change, not on every code edit.
Pin base images to sha256 digest, not a tag. Tags are mutable and can change under you — digests are immutable.
K8s concepts — your biggest gap right now
☸️ K8s = Docker concepts at cluster scale
Pod = the smallest deployable unit. Usually 1 container. Containers in the same Pod share the net namespace and can talk via localhost.
Deployment = manages N pod replicas. Handles rolling updates, rollback, and self-healing when pods crash.
Service = stable DNS name + load balancer across all pods. Survives pod restarts — clients always have a fixed address.
ConfigMap / Secret = inject config at runtime without baking it into the image. Secret is base64 encoded (not encrypted — use Vault for real secrets).
resources.requests = scheduling guarantee (node needs this much free). resources.limits = cgroup ceiling (enforcement, throttle or kill).
🔍 readinessProbe vs livenessProbe
readinessProbe: "should I send traffic here?" Fails → removed from the load balancer. Container keeps running. Use for: warming up, upstream dependency down.
livenessProbe: "is this container beyond self-recovery?" Fails → container is killed and restarted. Use for: deadlock, infinite loop, corrupted state.
Making liveness too sensitive is dangerous: if it fails during a DB slowdown, K8s restarts the container — turning a partial outage into a total one.
Liveness should only fail on things that genuinely require a restart to fix — not temporary slowness or upstream unavailability.
