Hybrid Core Allocation:
From Overallocation to Reliable Sharing

Section 01

The problem with the old model

Uber runs thousands of stateful workloads — databases, caches, storage nodes — on a fleet of physical machines. For years, their Odin orchestration system allocated CPU using three assumptions that turned out to be wrong:

Assumption 1 — averages are enough

One-minute CPU usage averages were used to size allocations. But many workloads are spiky — they idle for 50 seconds, then hammer all cores for 10 seconds. The average looks fine. The spike causes throttling.

Assumption 2 — cores are dedicated

Every core allocated to a workload was reserved exclusively for it. If a database was assigned 8 cores but only used 2 on average, 6 cores sat idle. Multiply this across thousands of machines — enormous waste.

Assumption 3 — utilization targets self-adjust

The system assumed CPU utilization targets could automatically adapt to failover scenarios. In practice, when traffic shifted unexpectedly, the targets were too slow to respond.

The result

Chronic over-provisioning — services sitting on reserved cores they rarely used — and occasional throttling when bursty services hit their limits during spikes.

The solution: hybrid allocation

Instead of only dedicated cores, every workload now gets two types of CPU:

Dedicated cores

Physically pinned to this workload only. No other container can run on them. Sized for the steady-state average load.

Shared cores

Drawn from a pool shared across all workloads on the host. Sized for burst headroom. Governed by cpu.shares weights during contention.

The key insight

Dedicated and shared cores solve different problems, so they are sized using different signals. Dedicated uses average CPU. Shared uses deviation (variance) from that average.

Section 02

cgroups, cpuset, and cpu.shares

cgroups (control groups) is a Linux kernel feature that lets the OS group processes together and then enforce resource limits on that group. Think of it as a fence the kernel draws around a container. Inside the fence, the container can only use what it's been allocated.

cgroups isn't just about CPU. It has many controllers (subsystems), each managing a different resource type. Uber's hybrid system uses two of them:

Figure 1 — Linux kernel cgroup controllers. Uber's hybrid system uses the cpuset and cpu controllers together.

cpuset.cpus — which cores

Writing a list of core IDs to this file physically pins the container to those cores. The kernel's scheduler will never schedule the process on any other core. This is how dedicated cores are enforced.

Example — pinning a container to cores 0 and 1 as dedicated, plus 2 and 3 as shared
# odin-agent writes this file directly at runtime
echo "0,1,2,3" > /sys/fs/cgroup/cpuset/kubepods/pod-abc123/cpuset.cpus

# cores 0,1 = dedicated to this container only
# cores 2,3 = shared pool (other containers also have 2,3 in their cpuset)

# Restrict RAM to NUMA node 0 (same socket as cores 0-3)
echo "0" > /sys/fs/cgroup/cpuset/kubepods/pod-abc123/cpuset.mems

cpu.shares — how much time under contention

cpu.shares is a relative weight. It is meaningless in isolation — it only takes effect when two or more containers are fighting for the same cores at the same time. When there is no contention, a container can freely use 100% of whatever cores are in its cpuset.

Mental model: votes in an election

If container A has 250 shares and container B has 750 shares, A gets 250/(250+750) = 25% of contested core time. B gets 75%. The denominator is always the sum of all active contenders — add a third container and everyone's fraction shifts.

The formula

cpu.shares = round( (dedicated_cores + shared_cores) × 100 ) Multiplying by 100 converts float shared_cores to an integer (kernel requirement),
and makes the number readable as "percentage of one CPU".
Worked example — 2 dedicated + 0.5 shared cores
# Workload needs: 2 dedicated cores + 0.5 shared cores
dedicated_cores = 2
shared_cores    = 0.5

cpu.shares = round( (2 + 0.5) × 100 ) = round( 250 ) = 250

# Write it:
echo "250" > /sys/fs/cgroup/cpu/kubepods/pod-abc123/cpu.shares

Figure 2 — cpu.shares as relative weights. The number only matters when containers compete for the same cores at the same time.

Section 03

NUMA — non-uniform memory access

Modern servers don't have one big pool of RAM. They have multiple CPU sockets, each soldered to its own local RAM bank. When a CPU core reads data from its own bank, it's fast (~60ns). When it reads from another socket's RAM, it has to cross an interconnect bus — that's ~120ns, twice as slow.

This physical reality is called NUMA. The penalty is real and measurable, especially for latency-sensitive services like databases.

Figure 3 — NUMA layout. Dedicated cores stay local to their NUMA node (fast path). Shared cores span both nodes deliberately.

Programmatic NUMA control

MethodWhat it doesHow Uber uses it
cpuset.mems Restricts RAM allocation to a specific NUMA node Set to same node as dedicated cores to keep memory local
cpuset.memory_migrate Migrates pages to the node where they're used most Tunable — requires benchmarking. Uber uses kernel defaults.
numactl --cpunodebind=0 Runs a process pinned to a specific NUMA node Not used directly — odin-agent handles this via cpuset
/proc/sys/kernel/numa_balancing Enables automatic NUMA page migration globally Kernel default. Uber lets kernel optimize local memory naturally.
Uber's NUMA strategy

Dedicated cores → placed on the same NUMA node as workload memory. Shared core pool → spread across both NUMA nodes so the host agent's own operations don't saturate one socket. No hard NUMA pinning for shared — let the Linux scheduler handle it.

Section 04

Full system architecture

This is the complete picture — every component from the Kubernetes control plane down to physical silicon, with both Uber-built and standard components labelled.

Figure 4 — Complete architecture. Amber = Uber-built. Teal = standard Kubernetes. Two paths converge on the same cgroup files: Path 1 (container birth) via kubelet → CRI plugin → containerd. Path 2 (live rescale) via odin-agent writing directly.

The two parallel paths

A critical detail: odin-agent and the CRI plugin are not sequential. They run in parallel and serve different lifecycle moments.

Path 1 — container birth (CRI plugin)

When a new container is created: kubelet calls the CRI to start it → the Uber CRI plugin intercepts that call → injects the cpuset config before containerd starts the process. This sets the initial cgroup values.

Path 2 — live rescale (odin-agent)

When the vertical scaler decides a running workload needs more or fewer cores: odin-agent writes directly to the cgroup files on the fly. No container restart needed. This is "in-place vertical scaling." For stateful services this matters enormously — restarting means copying all local disk data to a new machine.

Why in-place scaling matters for stateful services

A stateless web server can be killed and restarted cheaply. A database running on local NVMe disks cannot — moving it to another machine means copying terabytes of data, which is slow and risky. In-place CPU rescaling lets Uber right-size databases without relocating them at all.

Section 05

Commands at each layer

Most of Uber's components are daemons with internal reconcile loops — you don't invoke them with CLI commands. You invoke standard Kubernetes at the top. You inspect the result at the bottom. Everything in between is automated.

Figure 5 — Commands at each layer. You touch kubectl at the top and /sys/fs/cgroup at the bottom. Everything amber in between is automated by Uber's daemons.

Key commands reference

Deploy & scale — what you type
# Deploy a workload with resource requests
kubectl apply -f pod.yaml

# Scale replicas (each gets its own cgroup)
kubectl scale deployment/myapp --replicas=3

# Check what K8s thinks this pod has
kubectl describe pod <pod-name>
# Look for: Requests, Limits, Node fields
Inspect actual cgroup values — what odin-agent wrote
# Get a shell on the node itself
kubectl debug node/<node-name> -it --image=ubuntu

# Inside the node shell — read actual cpuset
cat /sys/fs/cgroup/cpuset/kubepods/pod<uid>/cpuset.cpus
# Expected output: 0,1,2,3  (dedicated + shared core IDs)

# Read actual cpu.shares
cat /sys/fs/cgroup/cpu/kubepods/pod<uid>/cpu.shares
# Expected output: 250  (for 2 dedicated + 0.5 shared)

# Read NUMA memory binding
cat /sys/fs/cgroup/cpuset/kubepods/pod<uid>/cpuset.mems
# Expected output: 0  (pinned to NUMA node 0)

# List running containers and their IDs
crictl ps
crictl inspect <container-id>
pod.yaml — the resource request that triggers Uber's scaler
apiVersion: v1
kind: Pod
spec:
  containers:
  - name: myapp
    resources:
      requests:
        cpu: "2500m"   # 2.5 cores = what K8s sees
        memory: "4Gi"
      limits:
        cpu: "3000m"   # ceiling = maps to cpu.quota
        memory: "4Gi"
# Uber's odin-agent then OVERRIDES the cpuset assignment
# based on its own dedicated+shared calculation.
# Standard K8s has no concept of hybrid core allocation.
Section 06

Known limitations and future work

Host-local decisions only

odin-agent runs on each machine independently and has zero visibility into other machines. It cannot say "Node 7 has spare shared cores, move some load there." The fix: move allocation decisions up to the workload scheduler, which has a fleet-wide view.

CPU allocation fragmentation

Over time, repeated workload placements and migrations leave CPU allocations scattered across NUMA nodes in non-optimal patterns. The proposed fix: a periodic defragmentation pass by odin-agent to repack allocations.

Shares skew under heavy contention

cpu.shares ratios hold well under light contention. Under severe contention (many workloads spiking simultaneously), the real distribution skews away from the intended ratio. Uber accepts this as rare enough to tolerate.

Some restarts still needed

In-place CPU rescaling works for most changes. Some workloads still require a container restart to pick up new CPU limits. Even then, restarting on the same node is far cheaper than migrating to a different machine.

The long-term vision

Uber's goal is configuration-free CPU management — the scaler automatically determines dedicated and shared allocation for every workload, eliminating manual CPU tuning entirely. The hybrid model is a step toward that: it makes the fleet self-adaptive rather than statically configured.
