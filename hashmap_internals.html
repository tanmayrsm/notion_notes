What is a HashMap?

foundation concept

You want to store and retrieve things by name, not by position. An array gives you instant access by index — but you'd have to scan everything to find by name.

The core problem

// array: fast by index, slow by name
arr[3]     // O(1) — you know the index
arr["Bob"] // doesn't exist — must scan all

// HashMap: fast by name
map.get("Bob") // O(1) — hash gives you the index

Three components — that's the entire concept

①
An array — the backbone. Fixed-size row of buckets. Gives O(1) jump-to-index.
②
A hash function — converts any key → a number → an array index. Same key always gives same index.
③
A collision strategy — when two keys land on the same index. Java uses chaining (linked list per bucket → tree at 8).

HashMap is NOT a primitive

Java has exactly 8 primitives: int long double float boolean char byte short. Everything else is a reference type. Map<K,V> map = new HashMap<>() — the variable map holds a 4-byte pointer on the stack. The actual object lives on the heap.

// The variable is NOT the object
Map<String,Integer> a = new HashMap<>();
Map<String,Integer> b = a;  // b points to SAME object
b.put("x", 1);
a.get("x");  // returns 1 — same heap object
⚡ Interview answer

HashMap is a reference type backed by a Node[] array. The variable holds a 4-byte compressed pointer. The object is on the heap. {k:v} syntax doesn't exist in Java — you always call new HashMap<>().

Hash Function

internals O(k) complexity

Two separate steps — most people confuse these

STEP 1 — key.hashCode()  →  O(length of key)
Defined on the object itself. For String: touches every character. Returns a raw 32-bit int. This is expensive. Java's String caches it after first call.
↓
STEP 2 — HashMap spread → bucket index  →  O(1)
Takes the 32-bit int, runs 2 integer ops. No string touched. Pure arithmetic.
// Step 1: String.hashCode() — O(n), cached after first call
int h = 0;
for (int i = 0; i < len; i++)
    h = 31 * h + chars[i];  // one op per character

// Step 2: HashMap.hash() — O(1), just 2 ops
int spread = h ^ (h >>> 16);     // XOR upper 16 bits into lower
int bucket = spread & (n - 1);   // bitwise AND (n must be power of 2)

Why XOR with upper 16 bits?

Small arrays like n=16 only use the lowest 4 bits of the hash. If a bad hashCode() has all entropy in high bits, everything collides in bucket 0. The XOR mixes high bits into low bits — better distribution.

Why must capacity be power of 2?

hash % n requires division — slow. hash & (n-1) is a single bitwise AND — only works when n is a power of 2. Java enforces this and uses the fast path.

Collisions & Chaining

pigeonholechaining

Why collisions are inevitable

Full 32-bit hash space = 2³² = ~4 billion possible values. You can't make a 4B slot array (that's 16GB for an empty map). So you compress: hash % 16. Compression means many different hashes land in the same slot.

// Different full hashes, same bucket — unavoidable
11 % 8 = 3
19 % 8 = 3   ← same bucket, totally different hash
27 % 8 = 3   ← same bucket again
Pigeonhole principle: If you have more keys than buckets, at least two keys must share a bucket. Collisions are mathematically guaranteed once you have more entries than capacity.

The add() algorithm

// HashMap.putVal() — simplified
int bucket = hash(key) & (n-1);

if (table[bucket] == null) {
    table[bucket] = new Node(hash, key, value, null); // fast path O(1)
} else {
    Node e = table[bucket];
    while (e != null) {
        if (e.hash == hash && e.key.equals(key))
            return; // duplicate — reject
        if (e.next == null) {
            e.next = new Node(hash, key, value, null); // append at tail
            if (binCount >= TREEIFY_THRESHOLD - 1)
                treeifyBin(tab, hash); // convert to RB tree
            break;
        }
        e = e.next;
    }
}

Treeify & Red-Black Tree

TREEIFY_THRESHOLD=8O(log n)

Why treeify?

Linked list lookup in a bucket = O(n). If 8 keys all hash to the same bucket, every contains() walks all 8. Red-Black tree = O(log 8) = 3 steps max. Same data, 2.7× faster search.

TREEIFY_THRESHOLD   = 8   // convert list → tree when bucket hits 8
UNTREEIFY_THRESHOLD = 6   // hysteresis: convert tree → list when drops to 6
MIN_TREEIFY_CAPACITY= 64  // if table < 64 slots: resize instead of treeify
Hysteresis gap (8→6): Prevents thrashing. Without it, adding and removing the 8th element repeatedly would constantly flip between list and tree.

How treeify actually works — step by step

Phase 1 — Each Node (32B) is replaced with a TreeNode (56B). Fields copied: hash, key, value, next. New fields: parent=null, left=null, right=null, red=false. Old Nodes → GC eligible.
Phase 2 — hd.treeify(table) called on the head. Walks the chain, inserts each node into BST by hash (then compareTo() for ties), then applies red-black coloring and rotations.
Phase 3 — Tree is live. parent/left/right form the RB tree. next/prev still intact for iteration. Memory: 8 × 56B = 448B vs old 8 × 32B = 256B. Worth it for O(log n) search.

Red-Black Tree rules

A plain BST can become a linked list if you insert sorted keys. RB rules prevent this:

Plain BST — sorted inserts
K1
 └─ K2
     └─ K3
         └─ K4 → O(n) !
RB Tree — always balanced
    K4(B)
   /     \
 K2(B)  K6(B)
 / \    / \
K1 K3  K5 K7
(R)(R) (R)(R)   → O(log n) ✓

The 4 RB invariants

  1. Every node is RED or BLACK
  2. Root is always BLACK
  3. No two consecutive RED nodes (red node's parent must be black)
  4. Every path root→null has the same number of BLACK nodes
These 4 rules mathematically guarantee tree height ≤ 2×log₂(n+1). After insert/delete, rotations + recoloring restore them in O(log n).

⚡ Interview answer

All keys in a bucket share the same bucket-hash (hash%n). To distinguish them inside the bucket, Java compares the full 32-bit spread hash (O(1) int compare) first — cheap early rejection. Then calls equals() only when full hashes match. The RB tree gives O(log n) node visits instead of O(n).

Load Factor & Resize

default 0.75doubles capacity
threshold = capacity × loadFactor  // 16 × 0.75 = 12
when size > threshold → resize    // double capacity, rehash all

What happens during resize

1. New array allocated — Node[oldCap * 2]. Capacity doubles.
2. Keys redistributed — Each key's new index = spread & (newCap-1). Either stays at same index OR moves to oldIndex + oldCap. The stored hash field is reused — hashCode() is never called again.
3. Collisions reduce — %32 has finer resolution than %16. Keys that collided before often separate into different slots.

contains() Deep Dive

hash checkequals()

Two-step check inside a bucket

// For each node in the bucket:
if (node.hash == searchHash          // O(1) int compare — cheap early reject
 && (node.key == searchKey           // reference equality O(1)
  || node.key.equals(searchKey))) {  // equals() — O(k) for strings, only when hash matches
    return node;
}

Full hash vs bucket hash — the key insight

All nodes in bucket 3 have the same hash%8 = 3. That check is useless. But Java stores the full 32-bit spread hash.

// Same bucket (hash%8 = 3), different FULL hashes
"Cab" → full hash = 0x00000003  → %8 = 3
"Bob" → full hash = 0x0000001B  → %8 = 3  ← different full hash!
"Cat" → full hash = 0x00000003  → %8 = 3  ← same full hash as "Cab"!

// Searching for "Cat":
check "Cab": full hash match → equals() → false   → skip
check "Bob": full hash NO match → skip equals() entirely ← O(1) save
check "Cat": full hash match → equals() → true  → FOUND
The full hash check is an optimization to avoid calling equals() unnecessarily. equals() on a long String is O(length). Skipping it via a cheap int compare saves real time at scale. But if two keys genuinely share the same full hash, equals() is unavoidable.

LinkedHashMap Internals

insertion order40 bytes/entry
LinkedHashMap extends HashMap. It has the SAME Node[] array. It just adds two extra pointer fields on each Entry: before and after.

The extra doubly-linked list

A doubly-linked list threads through ALL entries in insertion order. Each Entry node participates in BOTH the bucket chain (via next) AND the ordered list (via before/after) simultaneously.

// After put("Alice"), put("Bob"), put("Carol")
HashMap array: [···] [Bob@7] [···] [Alice@3] [···] [Carol@11] [···]
// random order based on hash
Doubly-linked list: head → Alice ⇄ Bob ⇄ Carol ← tail
// insertion order always

LRU Cache with LinkedHashMap

Map<String,Integer> lru = new LinkedHashMap<>(16, 0.75f, true) {

LinkedHashMap inherits HashMap's entire array+bucket machinery. It adds a doubly-linked list (before/after pointers, 8 extra bytes per entry) threading all entries in insertion order. get() is O(1) via hash. forEach() is O(n) via the linked list. Same array underneath.

Why HashMap Breaks with Threads

race conditionsilent data loss

The race condition

put() is three steps: read bucket → create node → write bucket. Not atomic.

Thread 1 — put("K1", 10)
1. read table[3] → null
2. create Node(K1)
3. write table[3] = K1 ✓
Thread 2 — put("K2", 20)
1. read table[3] → null (same time as T1!)
2. create Node(K2)
3. write table[3] = K2 ← OVERWRITES K1
K1 is silently lost. No exception. No warning. map.get("K1") returns null. map.size() returns 1 instead of 2. This is a race condition.

ConcurrentHashMap Internals

Java 7: segmentsJava 8: bin lockCAS

Java 7 — Segments (historical)

Array split into 16 fixed Segments. Each had a ReentrantLock. T1 writing bucket 0 and T2 writing bucket 2 — both in Segment 0 — T2 had to wait. Max parallelism: 16, hardcoded.

Segment<K,V>[] segments;   // 16 segments, each a ReentrantLock
int segIdx = (hash >>> segmentShift) & segmentMask;
segments[segIdx].lock();   // lock entire segment

Java 8 — Bin locking (what exists today)

Segments completely removed. Lock is now the first Node of each individual bucket. Finest possible granularity.

Node<K,V>[] table;  // plain array — no Segment class at all

// put() — 3 different paths:

// Path A: bucket is empty → CAS (zero locks)
casTabAt(table, bucket, null, newNode);
// single CPU instruction — atomic compare-and-swap
// if two threads race → one wins, one retries loop

// Path B: bucket has entries → lock just this bin
synchronized(table[bucket]) {
    // only this one bucket locked
    // all other buckets run freely
}

// Path C: MOVED marker → help with ongoing resize
helpTransfer(tab, f); // cooperative resize

get() — zero locks ever

V get(Object key) {
    Node[] tab = table;                        // volatile read
    Node e = tabAt(tab, (n-1) & h);           // Unsafe.getObjectVolatile()
    while (e != null) {
        if (e.hash == h && e.key.equals(key))
            return e.val;                      // val is volatile — always fresh
        e = e.next;                            // next is volatile
    }
    return null;
    // NO synchronized. NO lock. Reads are always safe.
}
Why reads are safe without locks: val and next on every Node are marked volatile. This means every thread always reads from main memory, never from a stale CPU cache. A write by Thread 1 is immediately visible to Thread 2's read.

size() — CounterCell[] trick

// naive: one shared counter → all threads fight over it
size++; // not atomic, or if AtomicLong → heavy contention

// CHM solution: each thread increments its OWN cell
CounterCell[] counterCells; // array of counters
long baseCount;             // fast path when no contention
// size() = baseCount + sum(counterCells)
// 100 threads → 100 different cells → zero contention

Why no null keys/values?

// Single-threaded: can disambiguate with containsKey()
map.get("x") == null  // absent OR present-with-null
map.containsKey("x")  // checks definitively

// Concurrent: between get() and containsKey(), another thread
// could add/remove "x". Result is ambiguous. So null is banned.
⚡ Interview answer

ConcurrentHashMap in Java 8 has no Segments. Lock granularity = one bucket. Empty bucket insert uses CAS (no lock). Non-empty bucket uses synchronized on the bin head node. get() uses zero locks — volatile fields ensure memory visibility. size() uses CounterCell[] to avoid contention on a shared counter. No null keys because the value is ambiguous in a concurrent context.

1. Mutable key trap

List<Integer> list = new ArrayList<>(Arrays.asList(1,2,3));
Set<List<Integer>> set = new HashSet<>();

list.add(4);              // mutates key! hashCode changes

Never mutate an object that's being used as a Map key or Set element. The element is stuck in the old bucket forever — unreachable, unremovable.

Set<BadKey> set = new HashSet<>();
set.add(new BadKey(5));
set.contains(new BadKey(5)); // FALSE — different identity hash → different bucket
set.add(new BadKey(5));      // adds a duplicate! set has 2 equal elements
// Rule violated: a.equals(b) MUST imply a.hashCode() == b.hashCode()

Hash DoS Attack

CVE-2011securityaffects Tomcat, Spring, Jetty

What is it — and why did it work?

Java's String.hashCode() is a public formula. The same string always produces the same hash on every JVM, everywhere. An attacker who knows the formula can craft thousands of strings that all produce identical hashCodes. Every crafted string lands in the same bucket — turning O(1) lookups into O(n) chain walks.

The collision family — "Aa" and "BB"

This isn't theoretical. There's a known infinite family of Java hash collisions:

// Java String hash: h = 31*h + char
"Aa".hashCode() = 31×65 + 97  = 2112
"BB".hashCode() = 31×66 + 66  = 2112  ← SAME hashCode!

// They compose — every combination also collides:
"AaAa", "AaBB", "BBAa", "BBBB"  → all hashCode = same value
// With n=15 prefix bits: 2^15 = 32,768 strings, all share one hashCode
// All land in the same bucket → lookup = O(32,768) per request

The attack vector — HTTP request parsing

An HTTP server parses POST body into a HashMap (query params, JSON fields, headers). The attacker sends a request with 10,000 crafted parameter names — all the same hashCode. Every get() call walks the entire 10,000-node chain. One request ties up a server thread for seconds. A hundred such requests saturates all CPU cores.

Real CVE (2011) — all major languages hit simultaneously: PHP, Python, Ruby, Java, .NET all used the same deterministic hash approach. Tomcat, Jetty, Spring, Rails — all vulnerable because they used HashMap-like structures to parse HTTP requests. Fixed across all languages within weeks of coordinated disclosure.

How Java fixed it — two layers

  • Java 7u6 — Hash seed randomisation (first line of defence): HashMap gets a random seed per JVM instance at startup. The bucket index becomes (hash ^ seed) & (n-1).   • Java 8 — Treeify (the real fix): Even if an attacker manages to land 10,000 keys in one bucket, the bucket auto-converts to a red-black tree at 8 entries. What CAS is — one sentence, then the detail

CAS = Compare And Swap. One single CPU instruction (CMPXCHG on x86). It says: "Change this memory location from OLD to NEW — but only if it currently holds OLD. If someone else already changed it, tell me so I can retry." Atomic at hardware level. About 10 nanoseconds. No OS. No sleeping. No context switch.

// What CAS does — pseudocode (actually ONE uninterruptible CPU instruction)
boolean CAS(location, expectedOld, newValue) {
    if (*location == expectedOld) {   // check and write happen atomically
        *location = newValue;
        return true;    // I won the race
    }
    return false;       // someone else changed it — I lost
}

// Using CAS for a counter — the spin loop pattern:
while (true) {
    int old = counter;               // read current value
    int newVal = old + 1;
    if (CAS(counter, old, newVal))
        break;                       // I won → done
    // CAS returned false → someone changed counter → loop, read new value, retry
    // Thread does NOT crash or throw — just retries
}

Cache Line False Sharing

64-byte cache lines@Contended10-40x throughput impact

How CPU caches work — the foundation

CPUs don't read individual bytes from RAM — they read 64-byte chunks called cache lines. If you need 1 byte at address X, the CPU fetches all 64 bytes containing X into L1 cache. This is why reading adjacent memory is fast.

The problem: If two threads write to different variables that happen to sit in the same 64-byte chunk, they constantly invalidate each other's cache — even though they're touching completely independent data.

The specific problem in ConcurrentHashMap

// CHM uses CounterCell[] for distributed size counting
// Thread 1 increments cell[0], Thread 2 increments cell[1]
// Different cells, different threads — should be zero contention.

// Memory layout WITHOUT padding:
// [cell[0] 8B][cell[1] 8B][cell[2] 8B]... all in ONE 64-byte cache line!

// Thread 1 writes cell[0] → CPU marks entire 64-byte line as MODIFIED
// Thread 2's copy of that line is now INVALID in its cache
// Thread 2 must re-fetch the whole line from RAM to write cell[1]
// Thread 1 then sees its copy is stale... and so on forever
// 10-40× performance degradation for two "independent" counters!

The fix — @Contended annotation

static final class CounterCell {
    volatile long value;
    CounterCell(long x) { value = x; }
}

// Effect: each CounterCell is padded to occupy its own cache line
// Thread 1 writes cell[0] → only its cache line invalidated
// Thread 2's cell[1] is on a completely different cache line → unaffected
// Zero false sharing. Full parallel write throughput.

// Memory cost: 8B per cell → ~128B per cell with padding (16× more)
// But throughput improvement: 10-40× — worth it
// Enable: -XX:-RestrictContended (needed in some JVM configs)

Your question — GC moves objects, so how does "pinning" work?

The word "pin" is misleading. Objects can still move Eden → Survivor → Old Gen. Here's the precise truth:

Your exact question — if x.intern() == y.intern() needs equals(), didn't you say no equals()?

There are two separate equals() calls that people conflate:

equals() Contract — All 5 Rules

Java spec requirementsTreeMap uses compareTo not equals

The 5 mathematical properties equals() must satisfy

HashMap and TreeMap both depend on equals() correctness — but they use it in different ways. Violating any rule causes silent bugs.

  • Reflexive — a.equals(a) must be true. An object must equal itself. Violating this: contains(x) never finds x even if x is in the map. Rare but happens with Double.NaN — NaN != NaN by IEEE 754 spec, so a HashSet containing NaN behaves strangely.
  • Symmetric — a.equals(b) must equal b.equals(a). Violating this: set.contains(a) returns true but set.contains(b) returns false for two logically equal objects. Which one returns true depends on which was put in the map first and which bucket it landed in.
  • Transitive — if a==b and b==c, then a==c. TreeMap uses compareTo() not equals() — if compareTo is not consistent with equals, TreeMap and HashMap disagree on whether two keys are the same key. Real source of production bugs when switching map types.
  • Consistent — same inputs → same output, every call. If equals() depends on mutable state that changes between calls, the map becomes permanently inconsistent. HashMap caches no equality results — it calls equals() fresh on every lookup.
  • Null-safe — a.equals(null) must return false, not throw. HashMap calls key.equals(node.key) during lookup. If this throws NPE instead of returning false, every lookup on that bucket crashes.

The critical difference: TreeMap uses compareTo(), not equals()

ciMap.put("apple", 2); // CASE_INSENSITIVE_ORDER.compare("Apple","apple") = 0

Fail-Fast vs Weakly-Consistent Iteration

How HashMap iteration actually works — your 1M bucket question

The iterator walks ALL buckets in array index order [0], [1], [2]... [n-1]. For each non-empty bucket it walks the entire chain or tree before moving to the next bucket. It doesn't skip empty slots — it reads each one and checks if it's null.

// Iterator internal logic — simplified
int currentBucket = 0;
Node currentNode  = null;

Node nextNode() {
    // if we're mid-chain, keep walking the chain first
    if (currentNode != null && currentNode.next != null) {
        currentNode = currentNode.next;
        return currentNode;
    }
    // find next non-empty bucket
    while (currentBucket < capacity) {
        currentNode = table[currentBucket++];
        if (currentNode != null) return currentNode; // found
    }
    return null; // fully done
}

Your question: "may or may not see concurrent puts/removes" — what does that actually mean in practice?

  • Entries that existed BEFORE iteration started: you will always see them. The iterator holds a reference to the live table array — those entries are there.
  • Entries added to buckets you've ALREADY visited: you will NOT see them. The iterator moved past those bucket indices already.
  • Entries added to buckets you HAVEN'T visited yet: you MIGHT see them. Depends on exact timing of when the put() and your iterator.next() interleave.
  • Entries removed while you're iterating: might still appear. The iterator holds node references — it won't crash even if that entry was removed from the map's perspective.
  • No exception ever: CHM has no modCount field. Nothing to check. Iterator never throws ConcurrentModificationException — by design.
Why weakly-consistent is the right trade-off: Snapshot-consistent iteration would require locking the entire map — killing all concurrent write throughput. At Uber scale, by the time you've iterated 10M entries the state has changed anyway. Weakly-consistent is safe, documented, and never deadlocks — it's a feature, not a compromise.
Interview answer: HashMap iterator is fail-fast — snapshots modCount at creation, throws CME on any structural modification during iteration. ConcurrentHashMap iterator is weakly-consistent — no modCount, never throws, may or may not see concurrent changes depending on whether affected buckets were already visited. Iteration cost = O(capacity + size) — oversized initial capacity wastes iteration time scanning empty slots.

Comparable vs Comparator in TreeMap

Comparator always winsTreeMap never calls equals()

Two ways TreeMap can order its keys

Comparable (natural ordering)
Interface implemented BY the key class itself.
Method: compareTo(T other)
Used when NO Comparator is given to TreeMap constructor.
Examples: String, Integer, LocalDate all implement it.
If key doesn't implement it → ClassCastException on first insert.
Comparator (custom ordering)
Passed TO TreeMap at construction time.
Method: compare(T a, T b)
Overrides natural ordering completely.
Examples: reverse order, case-insensitive, sort by field.
If provided → Comparator ALWAYS wins. 
// Natural ordering (Comparable)
TreeMap<String,Integer> m = new TreeMap<>();
m.put("banana",2); m.put("apple",1); m.put("cherry",3);
m.keySet(); // [apple, banana, cherry] — String.compareTo() = alphabetical

// Custom Comparator — reverse order (Comparator wins)
TreeMap<String,Integer> rev = new TreeMap<>(Comparator.reverseOrder());
rev.put("banana",2); rev.put("apple",1); rev.put("cherry",3);
rev.keySet(); // [cherry, banana, apple]

// Comparator and equals() DISAGREE — Comparator wins, equals() never called
TreeMap<String,Integer> ci = new TreeMap<>(String.CASE_INSENSITIVE_ORDER);
ci.put("Apple", 1);
ci.put("apple", 2); // compare("Apple","apple") = 0 → SAME KEY → overwrites
ci.size(); // 1

// "Apple".equals("apple") = false (HashMap: 2 entries)
// compare("Apple","apple") = 0  (TreeMap: 1 entry)
// Same strings. Different result. Silent if you switch map implementations.

The rule you must remember

TreeMap's entire concept of "same key" is compareTo() returning 0 — or Comparator.compare() returning 0. It never calls equals(). If your comparator says two keys are equal (returns 0), TreeMap merges them regardless of what equals() says. For consistent behaviour across HashMap and TreeMap: make compareTo() return 0 if and only if equals() returns true.

Interview answer: Comparator always beats Comparable in TreeMap. TreeMap never calls equals() — only compareTo() or Comparator.compare(). If compare() returns 0, the keys are the same. If your Comparator and equals() disagree, TreeMap and HashMap store different entry counts for the same data — a silent bug when switching implementations.

When NOT to Use HashMap

GC pressureboxing overheadstaff-level decision

The decision tree — pick the right tool first

if (keys are enum constants)          → EnumMap             // zero hashing, O(1)
if (keys/values are primitives)       → IntIntHashMap       // no boxing, 4B/entry
if (data exceeds heap / GC matters)   → Chronicle Map      // off-heap, 0 GC
if (membership only, no retrieval)    → Bloom Filter       // 10 bits/element
if (distributed across servers)       → Consistent Hashing // minimal remapping
if (LRU/TTL eviction needed)          → Caffeine Cache     // bounded + stats
if (sorted keys / range queries)      → TreeMap            // O(log n)
if (concurrent writes)                → ConcurrentHashMap  // per-bucket lock
else                                  → HashMap

Each situation explained

  • GC pauses too long → Chronicle Map (off-heap): 100M entries in-heap means GC must scan every Node object during marking. With G1GC at 32GB: stop-the-world pauses of 500ms+. Chronicle Map stores data in native memory — outside the JVM heap entirely. GC never sees it. Sub-ms lookups with zero GC pressure. Trade-off: keys and values must be serialized to bytes; slight overhead per access.
  • Primitive keys/values → IntIntHashMap (Eclipse Collections): HashMap<Integer,Integer> boxes every int into an Integer object — 16B per key, 16B per value, plus 32B Node. For 10M int→int entries: 640MB+. Eclipse Collections IntIntHashMap stores raw int primitives in arrays — no boxing, no Node objects. Same 10M entries: ~80MB. 8× more memory efficient with faster GC.
  • Membership-only → Bloom Filter: If you only need "have I seen this rideId before?" HashSet uses 32B+ per entry. Guava's BloomFilter uses ~10 bits per element with 1% false positive rate (never false negative). 10M entries: ~12MB vs ~320MB for HashSet. Perfect for deduplication checks at ingestion.
  • Distributed sharding → Consistent Hashing: Simple hash % 10 means adding an 11th server requires remapping 90% of keys. Consistent hashing maps keys to a ring — adding one server only remaps 1/n keys. Used by Uber's service mesh and Redis Cluster internally.
  • Fixed enum keys → EnumMap: If your keys are a known, fixed enum (RideStatus, PaymentMethod), HashMap hashes them needlessly. EnumMap is a plain array indexed by ordinal — zero hashing, fastest possible lookup.
Interview answer: HashMap is the right default for general use. But at scale the alternative matters: enum keys → EnumMap (no hashing). Primitive keys → IntIntHashMap (no boxing, 8× less memory). GC pressure from huge maps → Chronicle Map (off-heap). Membership-only → Bloom Filter (10 bits vs 32 bytes per element). Distributed sharding → consistent hashing. Staff-level = knowing the limits of HashMap and which alternative fits each constraint.

Design: Cache for 10M Ride Events

staff-level design questiondecision tree not single answer

The question

"Design a cache for 10 million ride events with sub-millisecond lookup." This is not "use a HashMap." The interviewer wants you to reason through every constraint and justify every choice out loud.

Walk through each decision

1. What are the keys?
rideId is typically a UUID String. If the same rideId is repeated across many requests → intern them (shared reference, == shortcut in HashMap). If they're truly unique UUIDs that never repeat → don't intern (pool bloat, permanent Metaspace). Better option: use long rideId instead of String — eliminates hashing cost entirely. Use LongObjectHashMap from Eclipse Collections for no-boxing access.
2. Initial capacity — pre-size to avoid mid-traffic resize
new ConcurrentHashMap<>((int)(10_000_000 / 0.75) + 1) = ~13.3M slots. Resizing 10M entries mid-traffic blocks all put() threads for 1-2 seconds while the new array is allocated and all nodes are rehashed. At Uber's latency SLAs this is unacceptable — pre-sizing is non-negotiable.
3. Thread safety model
ConcurrentHashMap. Multiple threads processing ride events simultaneously. Use computeIfAbsent for per-ride state initialisation — the lambda is called exactly once per rideId regardless of thread count. Avoid put + get pairs — they're not atomic as a unit.
4. Eviction strategy
Depends on access pattern: LRU access → Caffeine with maximumSize. TTL-based → Caffeine expireAfterWrite. Rides complete within ~30 minutes → TTL of 1 hour covers all active rides. Manual eviction thread → for domain-specific rules (e.g. evict when ride reaches COMPLETED state).
5. GC impact
10M live Node objects means GC must scan them all during marking. Options: ZGC for <1ms pauses at any heap size. Off-heap via Chronicle Map for zero GC impact. Caffeine with softValues() so GC can reclaim under memory pressure. G1GC with tuned region size if you must stay with default.

G1 vs ZGC

G1: pause grows with heapZGC: <1ms flat10% CPU overhead

Why GC matters for HashMap-heavy services

A HashMap with 10M entries = 10M live Node objects the GC must scan and track. With G1GC and a 32GB heap: marking those objects during a full GC can trigger stop-the-world pauses of 200–500ms. At Uber's p99 latency targets (typically <100ms), this is a SLA violation every time GC fires.

G1GC — default since Java 9

  • How it works: Divides heap into equal-sized regions (~1–32MB each). GC operates in concurrent phases but the final marking and evacuation steps require stop-the-world pauses where all application threads freeze.
  • Pause target: Configurable, default 200ms. At 32GB heap with 100M live objects: actual observed pauses often 500ms–1s in production.
  • The fundamental problem: G1's pause time grows with the number of live objects and regions to scan. More entries in your HashMap = longer GC pauses. The two things (data scale and GC health) fight each other.

ZGC — production-ready since Java 15

  • How it works: Does marking AND object relocation concurrently with the application — application threads never fully stop. Uses two techniques: coloured pointers (extra bits embedded in every object reference encoding GC state — "has this object moved?"), and load barriers (a small piece of JVM-injected code that runs at every object read to check if the referenced object has been relocated and redirect if so).
  • Pause time: <1ms regardless of heap size. 1TB heap with 500M live objects: still <1ms pauses. The pause time only depends on the number of GC roots (thread stacks, static fields) — not on heap size or live object count.
  • Why it's flat while G1 grows: G1's stop-the-world phases scan and evacuate O(live objects). ZGC's stop-the-world phases only scan GC roots — O(number of threads × stack depth), which is tiny and constant regardless of heap size.
// Enable ZGC:
java -XX:+UseZGC -Xmx32g -Xms32g MyApp

// Pause comparison with large HashMap-heavy service:
G1GC  @ 16GB heap:  100-300ms pauses   ← violates p99 SLA
G1GC  @ 32GB heap:  300-800ms pauses   ← much worse
ZGC   @ 16GB heap:  <1ms pauses        ← within SLA
ZGC   @ 32GB heap:  <1ms pauses        ← flat, doesn't grow!
ZGC   @ 1TB heap:   <1ms pauses        ← still flat

ZGC trade-offs — it's not free

  • CPU overhead (~5–15%): Load barriers are injected at every object read in compiled code. Every time your application reads an object reference (which is constantly), a small check runs. This is the price of concurrent relocation.
  • Throughput: ZGC has slightly lower throughput than G1 for batch workloads (fewer total operations per second). For latency-sensitive services with SLA requirements, the consistent <1ms pauses are worth the throughput cost.
  • When to use ZGC: Heap > 4GB AND latency SLA < 100ms AND you have many long-lived objects (like a large HashMap cache). ZGC is the right choice for Uber's ride-event processing and pricing services.
  • When to stick with G1: Heap < 4GB, or batch workloads where maximum throughput matters more than consistent latency, or you can't afford the 10% CPU overhead.
Interview answer: G1GC pause time grows with heap size — at 32GB with a large HashMap cache: 500ms+ pauses possible. ZGC achieves <1ms pauses regardless of heap size by doing marking and object relocation concurrently using coloured pointers and load barriers. Trade-off: ~10% more CPU from load barriers. For Uber's latency-sensitive services with 10M-entry caches, ZGC is the right choice — a random 500ms G1 pause violates the p99 SLA every time it fires.
