Chapter 1

Strings & TTL

The simplest structure — one key maps to one value. The value can be a plain string, a number, or serialized JSON. TTL (time-to-live) makes keys self-destruct after N seconds — no cron job needed.

Basic commands

INPUT
SET  user:abc:name "Tarun"
GET  user:abc:name

SET  session:tok123 "user-abc"  EX 30   # expires in 30 seconds
TTL  session:tok123                        # seconds remaining
# wait 30 seconds...
GET  session:tok123                        # gone

SET  counter 0
INCR counter                              # atomic +1
INCR counter
INCRBY counter 10
GET  counter
output OK "Tarun" OK (integer) 28 (nil) OK (integer) 1 (integer) 2 (integer) 12 "12"

Complexity

GET / SET
O(1)
Single hashtable lookup by key hash. ~1µs on M4 Max.
INCR / DECR
O(1)
Atomic integer increment. No lock needed — Redis is single-threaded.
TTL check
O(1)
Expiry stored alongside the value in the same hashtable entry.

How TTL works internally

Internal algorithm

Redis stores expiry as an absolute Unix timestamp (milliseconds) in a separate expires dict — a second hashtable that maps key → expiry_ms. When you call TTL key, Redis does expires[key] - now().

Lazy expiry: when you GET a key, Redis first checks the expires dict. If expired, it deletes the key right then and returns nil. Keys are not deleted the moment they expire — only when accessed or found by the active sweep.

Active sweep: 10 times per second Redis randomly samples 20 keys from the expires dict, deletes any that are expired. If more than 25% of the sample was expired, it repeats immediately. This keeps memory from filling up with keys that nobody ever reads.

Why not a timer per key: millions of timers would destroy memory. The lazy + probabilistic sweep approach keeps expiry cheap at scale.

In FoodFlash

Auth tokens

SET session:{token} {userId} EX 86400 — 24 hour expiry. Token validates in O(1). No DB hit on every request.

Typing indicators

SET typing:{orderId}:{userId} true EX 3 — expires in 3s automatically. No cleanup code needed.

Chapter 2

Hashes

A Hash stores a map of field→value pairs under one key — like a row in a database, or a flat object. The key benefit over a JSON string: you can read or update one field without touching the rest.

Basic commands

INPUT
# store an order object
HSET order:123  status "PENDING"  user_id "abc"  amount "380"

HGET    order:123  status          # get one field
HGETALL order:123                  # get everything
HMGET   order:123  status amount   # get specific fields

HSET    order:123  status "CONFIRMED"   # update one field only
HGET    order:123  status

HDEL    order:123  amount
HEXISTS order:123  amount
HLEN    order:123
output (integer) 3 # fields set "PENDING" 1) "status" 2) "PENDING" 3) "user_id" 4) "abc" 5) "amount" 6) "380" 1) "PENDING" 2) "380" (integer) 0 # 0 = field existed and was updated "CONFIRMED" (integer) 1 (integer) 0 # doesn't exist (integer) 2 # remaining fields

Nested objects — flatten into field names

INPUT — encoding nesting as field name paths
# {status:"PENDING", restaurant:{id:"r1", name:"Dominos", addr:{city:"Hyd"}}}
HSET order:123
  status           "PENDING"
  restaurant:id    "r1"
  restaurant:name  "Dominos"
  restaurant:addr:city  "Hyd"

HGET  order:123  restaurant:addr:city
HGET  order:123  restaurant:name
output "Hyd" "Dominos"

Complexity

HGET / HSET
O(1)
Two hashtable lookups: outer key → hash object, then field inside it.
HGETALL
O(N)
N = number of fields. Iterates all fields. Avoid on hashes with thousands of fields.
HMGET
O(N)
N = number of fields requested, not total fields. Always prefer over HGETALL when you need specific fields.

How Hashes work internally

Internal algorithm — two encodings

Listpack (small hashes): when a hash has fewer than 128 fields AND all values are under 64 bytes, Redis stores it as a listpack — a compact, contiguous byte array in memory. No pointers, no hashtable overhead. Field lookup is O(N) linear scan, but N is so small (<128) that it's faster in practice than a hashtable due to CPU cache locality. Every field is right next to the previous one in memory.

Hashtable (large hashes): once either threshold is exceeded, Redis converts to a proper hashtable. Now HGET is O(1) true average-case — hash the field name, find the bucket, walk the chain. But memory jumps significantly because each entry needs a pointer.

Why this matters for you: our order cache hashes are small (10-15 fields), so Redis keeps them as listpacks. They fit in one or two CPU cache lines. HGET on a listpack is actually faster than a hashtable O(1) because there's no pointer chasing — just scanning adjacent bytes in L1 cache.

Chapter 3

Lists

A doubly-linked list of strings. Fast O(1) push and pop at both ends. Indexed access is O(N). The killer feature: BRPOP — blocking pop that makes lists a natural job queue without polling.

Basic commands

INPUT
LPUSH order:123:timeline "ORDER_PLACED"
LPUSH order:123:timeline "RESTAURANT_CONFIRMED"
LPUSH order:123:timeline "AGENT_ASSIGNED"
LPUSH order:123:timeline "DELIVERED"

LRANGE order:123:timeline 0 -1   # all elements
LRANGE order:123:timeline 0 1    # last 2 events
LLEN   order:123:timeline
LINDEX order:123:timeline 0       # newest event
RPOP   order:123:timeline         # remove oldest
output (integer) 1 (integer) 2 (integer) 3 (integer) 4 1) "DELIVERED" # newest first (LPUSH adds to head) 2) "AGENT_ASSIGNED" 3) "RESTAURANT_CONFIRMED" 4) "ORDER_PLACED" 1) "DELIVERED" 2) "AGENT_ASSIGNED" (integer) 4 "DELIVERED" "ORDER_PLACED"

As a job queue — BRPOP

TERMINAL 1 — worker waiting for jobs
BRPOP jobs:email 0    # blocks forever (0 = no timeout)
# cursor blinks... worker is sleeping
TERMINAL 2 — producer pushes a job
LPUSH jobs:email "send-receipt:order-123"
terminal 1 instantly wakes up 1) "jobs:email" 2) "send-receipt:order-123" # took 0.3ms from LPUSH to BRPOP returning

Complexity

LPUSH / RPUSH / LPOP / RPOP
O(1)
Head and tail pointers. Constant time regardless of list size.
LRANGE
O(S+N)
S = offset from head, N = elements returned. LRANGE 0 -1 on a 10k list = O(10k).
LINDEX
O(N)
Must traverse linked list from head. LINDEX 0 is O(1), LINDEX 5000 is O(5000).

Internally — quicklist

Internal algorithm

Redis lists use a quicklist — a doubly-linked list of listpack nodes. Instead of one node per element (wasteful pointer overhead), each node is a small listpack holding up to 128 elements as a packed byte array. So the structure is: linked list of arrays.

This gives you the best of both: O(1) push/pop at ends (linked list property), and good memory density (listpack arrays reduce pointer overhead by ~8x vs a naive linked list). LINDEX traversal walks the linked list of nodes, then scans inside a listpack — still O(N) overall but with smaller constant.

BRPOP blocking mechanism: when no elements exist, Redis registers the client in a wait list for that key. When LPUSH fires, Redis checks the wait list before even returning to the event loop — wakes the blocked client directly. This is why BRPOP latency is sub-millisecond, not the 1-10ms you'd get from polling.

Chapter 4

Sets

An unordered collection of unique strings. No duplicates ever. The power is in set operations — intersection, union, difference — all done server-side in one command. No sorting, no scores.

Basic commands

INPUT
SADD restaurant:r1:tags "pizza" "italian" "veg-friendly"
SADD restaurant:r2:tags "pizza" "fast-food" "delivery-only"

SMEMBERS  restaurant:r1:tags
SISMEMBER restaurant:r1:tags "pizza"    # is "pizza" in set?
SCARD     restaurant:r1:tags             # count

SINTER restaurant:r1:tags restaurant:r2:tags  # common tags
SUNION restaurant:r1:tags restaurant:r2:tags  # all tags
SDIFF  restaurant:r1:tags restaurant:r2:tags  # in r1 but not r2

SADD restaurant:r1:tags "pizza"   # duplicate — silently ignored
SCARD restaurant:r1:tags
output (integer) 3 (integer) 2 1) "veg-friendly" 2) "italian" 3) "pizza" (integer) 1 # yes (integer) 3 1) "pizza" 1) "pizza" 2) "italian" 3) "veg-friendly" 4) "fast-food" 5) "delivery-only" 1) "italian" 2) "veg-friendly" (integer) 0 # 0 new members added (already existed) (integer) 3 # still 3, no duplicate added

Complexity

SADD / SREM / SISMEMBER
O(1)
Hashtable lookup. Average constant time.
SMEMBERS
O(N)
Must return all N members. Avoid on large sets.
SINTER / SUNION / SDIFF
O(N×M)
N = smallest set size, M = number of sets. Intersection walks smallest set, checks each in others.

Internally — intset vs hashtable

Internal algorithm

Intset: if all members are integers and count is under 512, Redis stores the set as a sorted array of integers — an intset. SISMEMBER does binary search: O(log N) but with tiny N and perfect cache locality, faster in practice than O(1) hashtable.

Hashtable: as soon as any string member is added or count exceeds 512, converts to a hashtable. Each member is a key in the hashtable with a null value. SADD hashes the member, checks the bucket, adds if absent. Deduplication is free — hashtable lookup handles it.

SINTER algorithm: takes the smallest set, iterates every member, checks if it exists in all other sets via O(1) hashtable lookup. Total: O(smallest_set × num_sets). Always put your smallest set first in SINTER.

Chapter 5

Sorted Sets

Like a Set but every member has a float score, and members are always kept sorted by score. The most complex and powerful Redis structure — backed by a skip list internally. Used for leaderboards, delay queues, and range queries by score.

Basic commands

INPUT
ZADD leaderboard 450 "restaurant-dominos"
ZADD leaderboard 380 "restaurant-pizzahut"
ZADD leaderboard 510 "restaurant-mcdonalds"
ZADD leaderboard 290 "restaurant-kfc"

ZRANGE    leaderboard 0 -1 WITHSCORES   # low → high
ZREVRANGE leaderboard 0 1  WITHSCORES   # top 2
ZRANK     leaderboard "restaurant-dominos" # 0-indexed rank
ZSCORE    leaderboard "restaurant-dominos"
ZINCRBY   leaderboard 50 "restaurant-kfc"  # add 50 to score

# range by score — all restaurants rated 400-500
ZRANGEBYSCORE leaderboard 400 500 WITHSCORES
output 1) "restaurant-kfc" 2) "290" 3) "restaurant-pizzahut" 4) "380" 5) "restaurant-dominos" 6) "450" 7) "restaurant-mcdonalds" 8) "510" 1) "restaurant-mcdonalds" 2) "510" 3) "restaurant-dominos" 4) "450" (integer) 2 # rank 2 (0=lowest) "450" "340" # kfc now 340 1) "restaurant-dominos" 2) "450"

Delay queue pattern — using score as unix timestamp

INPUT — schedule a job for future execution
# schedule order timeout check 15 minutes from now
ZADD delayed:jobs 1736944800 "timeout:order-123"
ZADD delayed:jobs 1736945100 "timeout:order-124"

# worker polls every second: get all jobs due NOW
ZRANGEBYSCORE delayed:jobs 0 1736944900  # up to current unix time

# process them, then remove
ZREM delayed:jobs "timeout:order-123"

Complexity

ZADD / ZREM / ZSCORE / ZRANK
O(log N)
Skip list insertion/deletion. N = total members in sorted set.
ZRANGE / ZRANGEBYSCORE
O(log N + M)
log N to find start position, then M to traverse results.
ZINCRBY
O(log N)
Remove old position, re-insert at new score. Two skip list operations.

Internally — skip list + hashtable

Internal algorithm — skip list

A sorted set is backed by two data structures simultaneously: a skip list for score-ordered traversal and range queries, and a hashtable for O(1) member→score lookups (ZSCORE, ZRANK).

Skip list: imagine a linked list where each node also has "express lanes" — pointers that skip ahead by 2, 4, 8, 16 nodes. To find where to insert score 450, you start at the top express lane, skip forward until you overshoot, drop down a lane, repeat. Expected traversal: O(log N) hops. Unlike a balanced BST (AVL/Red-Black), a skip list is simpler to implement and cache-friendly because forward pointers are often in the same memory region.

Why both structures: skip list alone can't do O(1) ZSCORE (you'd have to scan). Hashtable alone can't do range queries. Together: ZRANGEBYSCORE uses skip list, ZSCORE uses hashtable. Memory cost is roughly 2× a simple list, but you get both query shapes in one structure.

Small sorted sets: under 128 members with values under 64 bytes, Redis uses a listpack instead of a skip list — same listpack encoding as Hashes. Promotes to skip list+hashtable on overflow.

Chapter 6

GEO

GEO commands let you store coordinates and query by radius — without PostGIS, without spatial indexes. Internally it's just a Sorted Set with coordinates encoded as scores. The encoding is the clever part.

Basic commands

INPUT
GEOADD drivers:locations 78.4867 17.3850 "agent-raju"
GEOADD drivers:locations 78.4960 17.3950 "agent-priya"
GEOADD drivers:locations 78.5100 17.4100 "agent-kumar"

GEOPOS  drivers:locations "agent-raju"
GEODIST drivers:locations "agent-raju" "agent-priya" km

# find all agents within 5km of a point, sorted nearest first
GEORADIUS drivers:locations 78.4867 17.3850 5 km ASC

# with distance in result
GEORADIUS drivers:locations 78.4867 17.3850 5 km ASC WITHCOORD WITHDIST
output 1) 1) "78.48670" 2) "17.38500" "1.2341" # km between raju and priya 1) "agent-raju" 2) "agent-priya" 3) "agent-kumar" 1) 1) "agent-raju" 2) "0.0000" # 0km — it's the origin point itself 3) 1) "78.48670" 2) "17.38500"

Complexity

GEOADD
O(log N)
Encodes coords as geohash score, inserts into sorted set. N = existing members.
GEORADIUS
O(N+log M)
N = members in radius, M = total members. Uses score range query on sorted set.
GEODIST / GEOPOS
O(log N)
Looks up geohash score in sorted set, decodes back to coordinates.

Internally — geohash as sorted set score

Internal algorithm — 52-bit geohash

Geohash encoding: latitude and longitude are each converted to a binary fraction, then interleaved bit by bit into a single 52-bit integer. For example: lat=17.385 → 01101..., lng=78.487 → 10110... → interleaved: 100110... This integer becomes the sorted set score.

Why interleaving works for proximity: coordinates that are geographically close produce geohash integers that are numerically close. So "find all points within 5km" becomes "find all scores in range [hash-delta, hash+delta]" — a ZRANGEBYSCORE query on the skip list. No spatial index needed.

GEORADIUS algorithm: (1) compute the geohash of the center point, (2) calculate the score delta corresponding to the radius in degrees, (3) run ZRANGEBYSCORE to get candidates, (4) filter by actual Haversine distance (because geohash ranges are rectangular, not circular — some corner candidates are out of radius). Step 4 is why it's O(N+log M) not just O(log M).

Precision tradeoff: 52-bit geohash gives ~0.6mm precision. More than enough for delivery driver tracking.

Chapter 7

Pub/Sub

Publish/Subscribe is a messaging layer built into Redis. Publishers send to channels. Subscribers listening to a channel receive messages instantly. No persistence — if no subscriber is listening when a message is published, it's gone. This is both its power (sub-millisecond) and its limitation.

Basic commands — open two terminals

TERMINAL 1 — subscriber (driver's chat server instance)
SUBSCRIBE chat:order-123
# blocks here, waiting for messages
terminal 1 output immediately 1) "subscribe" 2) "chat:order-123" 3) (integer) 1 # 1 subscription active
TERMINAL 2 — publisher (customer's chat server instance)
PUBLISH chat:order-123 "Are you nearby?"
PUBLISH chat:order-123 "I can see your location"
terminal 1 receives instantly (<1ms) 1) "message" 2) "chat:order-123" 3) "Are you nearby?" 1) "message" 2) "chat:order-123" 3) "I can see your location"
Pattern subscribe — multiple channels at once
PSUBSCRIBE chat:*         # all chat channels
PSUBSCRIBE order:*:status # all order status channels

PUBSUB CHANNELS           # list all active channels
PUBSUB NUMSUB chat:order-123  # count subscribers on channel

Complexity

PUBLISH
O(N+M)
N = subscribers on channel, M = pattern subscriptions to check. Each subscriber gets a copy pushed.
SUBSCRIBE
O(N)
N = channels being subscribed. Registers client in channel's subscriber list.

Pub/Sub vs Kafka for chat — why we use both

Redis Pub/Sub — real-time delivery

Customer on server-instance-3, driver on server-instance-7. Customer sends message → instance-3 publishes to Redis channel → instance-7 (subscribed) receives in <1ms → pushes to driver's WebSocket. Zero message history. If driver is offline: message is lost.

Kafka — durable pipeline

Simultaneously, instance-3 publishes same message to Kafka chat.message topic → Cassandra writer consumer persists it. Driver comes back online → loads chat history from Cassandra. Kafka is the durability layer, Redis is the speed layer.

The critical gotcha: Pub/Sub has zero persistence. If Redis restarts while messages are in flight, they vanish. If your subscriber is slow and can't keep up, Redis drops messages — there's no queue backing up. For fire-and-forget real-time fanout it's perfect. For anything that must be guaranteed delivered, use Kafka or Redis Streams instead.

Internally — push model, no polling

Internal algorithm

Redis maintains a dictionary mapping channel name → list of subscribed clients. When PUBLISH fires, Redis looks up the channel, iterates the subscriber list, and pushes the message directly into each client's output buffer — all within the same event loop tick. No disk I/O, no serialization overhead beyond the network write.

Why it's faster than Kafka for this use case: Kafka writes to disk (even with acks=1, the leader writes before acknowledging). Redis Pub/Sub never touches disk. It's purely in-memory socket writes. The tradeoff is exactly that: Kafka's disk write is what gives you durability and replay. Redis's lack of disk write is what gives you sub-millisecond latency.

Chapter 8

Memory & Persistence

Redis is an in-memory database — all data lives in RAM by default. This is why it's fast and why it's volatile. Understanding persistence modes tells you exactly what you can and can't trust Redis to survive.

Prove it — restart Redis, data is gone

INPUT
SET important:data "dont lose me"
GET important:data

# in your Mac terminal (not redis-cli):
docker restart redis

# back in redis-cli:
GET important:data
output OK "dont lose me" # restarting... (nil) # gone. RAM was cleared on restart.

Three persistence modes

ModeWhat it doesData loss on crashUse when
None (default)Pure RAM. Nothing written to disk.Everything since last restartPure cache — you can reconstruct from source of truth
RDB snapshotsFull dump to disk every N seconds or M writes. SAVE / BGSAVEUp to N seconds of writesBackup and restore. Not for durability.
AOF (appendonly)Every write command appended to a log file. Replayed on restart.At most 1 second (fsync every second)When you need durability and can accept slight latency

The design rule for FoodFlash

Redis holds what you can reconstruct. Postgres/Cassandra holds what you can't afford to lose.

Auth tokens: lose them → user re-logs in. Fine.
Agent locations: lose them → next ping arrives in 3s. Fine.
Typing indicators: lose them → nobody sees "typing". Fine.
Order data: lose it → customer charged, no order in system. NOT fine → Postgres.
Chat history: lose it → conversation gone → Cassandra.

Never store in Redis-only anything whose loss would cause a business incident.

Memory — what Redis actually uses RAM for

INPUT — check memory usage
INFO memory
MEMORY USAGE order:123       # bytes for one key
DBSIZE                        # total keys
How Redis manages memory

jemalloc: Redis uses jemalloc as its memory allocator — better fragmentation characteristics than glibc malloc for Redis's mixed allocation pattern (many small objects).

maxmemory + eviction: set maxmemory 2gb in redis.conf. When limit is hit, Redis evicts keys based on policy: allkeys-lru (evict least recently used, any key), volatile-lru (evict LRU keys that have TTL set only), allkeys-random. For a pure cache, allkeys-lru is standard. LRU is approximated — Redis samples 10 random keys and evicts the least recently used from that sample, avoiding the overhead of a true LRU linked list.

Memory per key overhead: every Redis key has a base overhead of ~50–70 bytes (key string, expiry dict entry, metadata). A key with value "1" costs more than 1 byte — it costs ~70 bytes total. This is why you don't use Redis for millions of tiny keys without considering memory budget.

Cache-aside pattern — how menu caching works

pseudocode — Go API Gateway
func getMenu(restaurantId string) Menu {
    // 1. check cache first
    cached := redis.Get("restaurant:" + restaurantId + ":menu")
    if cached != nil {
        return parse(cached)   // cache hit — ~1ms
    }

    // 2. cache miss — go to postgres
    menu := postgres.query("SELECT * FROM menu_items WHERE restaurant_id = ?", restaurantId)

    // 3. populate cache for next 10 minutes
    redis.Set("restaurant:" + restaurantId + ":menu", serialize(menu), 600)

    return menu   // ~15ms on cache miss
}
Why not always use Redis for menu? Menu changes (restaurant adds/removes item) must invalidate the cache. You'd call DEL restaurant:{id}:menu in the update flow. If you forget, customers see stale menus for up to 10 minutes. TTL is the safety net — even if your invalidation logic has a bug, the cache self-heals in 10 minutes.
